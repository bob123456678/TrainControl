## B - Medium

### MB-B1. The Lite repaint now takes the Layout monitor on the EDT

[TrainControlUI.java:15658](../../src/org/traincontrol/gui/TrainControlUI.java) (`repaintAutoLocListLite` -
the `ac66dc7` fix runs the per-panel `updateState` loop inside the `invokeLater`, where the raw
thread used to be), [AutoLocomotiveStatus.java:203](../../src/org/traincontrol/gui/AutoLocomotiveStatus.java)
(`updateState`'s standing-by branch: `getPossiblePaths` - `synchronized` on the Layout monitor -
plus the synchronized `getTimetableStartingPoint` legend read), the trigger
([TrainControlUI.java:15404](../../src/org/traincontrol/gui/TrainControlUI.java) - the graph callback
fires Lite at **every path start and end**), against
[Layout.java](../../src/org/traincontrol/automation/Layout.java) (`configureAndLockPath`:
`synchronized (this)` across its per-command sleeps, half a second to two seconds per path).

`UH-B4` was real - `updateState` mutates Swing, and running it on a raw thread per callback is what
made the `UH-B5` dispatch misroute reachable - so moving it onto the EDT was the right direction.
What moved along with it was never priced:

- **The stall.** The standing-by branch is skipped during full autonomy (`isAutoRunning()` is true),
  but in **semi-autonomous** operation with two or more trains it is live: train B arrives, its
  completion callback fires Lite, and the EDT runs `getPossiblePaths` for every idle panel - while
  train A is mid-`configureAndLockPath` holding that same monitor through its command sleeps. (A
  configuring locomotive is not yet in `activeLocomotives`, so its own panel takes the standing-by
  branch too.) The whole UI freezes until A's switches are thrown. This is `IR-B2` in the mode its
  fix did not cover: that fix hoisted the *timetable* snapshot off the EDT precisely because
  "`configureAndLockPath` holds that monitor through its command sleeps"; Lite now does the thing
  the hoist exists to prevent.
- **The baseline cost.** Even uncontended, full path enumeration (BFS per destination pair, per idle
  locomotive panel) now runs on the EDT at every path start and end during semi-autonomous
  operation. Before `ac66dc7` this work ran off the EDT - wrongly threaded, but free.

B on the `FCR-B3`/`IR-B2` precedent: an unprompted, recurring UI stall in a supported mode,
introduced by this release's own fix round. Bounded honestly: it needs semi-autonomous operation
(manual double-click dispatches), and the multi-second stall further needs an arrival to overlap
another train's configuration window - a few times a session rather than every callback; the
per-callback enumeration hitch, however, is every start and end.

**Fix shape:** the split the cycle has already used twice (`IR-B2`, `TCR-C1`): gather off the EDT,
marshal the apply. Lite computes each panel's path list (and the two legend lookups) on its calling
thread or a worker, then hands `updateState` a finished snapshot inside the `invokeLater`. That
keeps `UH-B4`'s fix - all Swing mutation stays on the EDT - and `UH-B5`'s, since the dispatch index
is still resolved against the list the user saw.

## C - Low

### MB-C1. The callback armor covers one door of three

[Layout.java:3237](../../src/org/traincontrol/automation/Layout.java) (the `ac66dc7` try/catch, at
the dispatch-time fire site) against lines 3489/3499 (the milestone loop, incl. the non-atomic
repaints) and 3537/3544 (the completion loop) - the same `callback.apply` on the same driving
threads, unwrapped.

`UH-C2` named the dispatch site because that is where a throw once stranded the `activeLocomotives`
entry. Two corrections from reading master's enforcing code:

1. **The stranding claim is stale on both the finding and the new comment.** `executePath`'s
   `RuntimeException` wrapper ([Layout.java:3095](../../src/org/traincontrol/automation/Layout.java),
   from the July cycle) already removes the entry, stops the locomotive, logs, and rethrows - so an
   uncaught callback throw did not wedge the layout; it aborted the run. The comment above the new
   catch says "the wedged state that only reloading the graph clears", which is what the code did
   *before* that wrapper existed. Worth correcting so the next reader calibrates against the right
   failure mode.
2. **The twins are still live.** A callback throw in the milestone or completion loop unwinds to the
   wrapper and rethrows: `runLocomotive`'s dispatch loop
   ([Layout.java:2414](../../src/org/traincontrol/automation/Layout.java)) has no try around
   `executePath`, so the autonomy thread for that locomotive dies and it is never dispatched again
   that session - silently, but for the logged exception; a timetable run stops via
   `executeTimetable`'s catch; a semi-autonomous dispatch thread dies without its failure dialog. The
   path is deliberately left locked by the wrapper, so recovery is a reload either way.

The reachable trigger shrank in the same commit - moving Lite's Swing work onto the EDT means the
repaint no longer throws on the driving thread - but the graph callback still mutates GraphStream
attribute maps on driving threads (`UH-C2`'s other half, unfixed by design), so the class is not
empty. One try/catch at each remaining loop, same as the first.

### MB-C2. Two route editors, one guard, different threads

[TrainControlUI.java:11222](../../src/org/traincontrol/gui/TrainControlUI.java) and line 12387 (the
only-one-editor guards, on the spawned worker threads) against lines 11256 and 12407 (the
assignments, now inside `invokeLater` per the backported EDT-realisation fix).

The backport correctly moved `RouteEditor` construction onto the EDT. But each entry path checks
`routeEditor != null && isVisible()` on its worker thread *before* posting the construction - so two
clicks in quick succession (a double-click on the Add Route button suffices) can both pass the check
while neither assignment has run, and both post. Result: two editors open, the field holds whichever
was assigned last, and the capture path
([TrainControlUI.java:2765](../../src/org/traincontrol/gui/TrainControlUI.java)) appends captured
commands to that one - while the user may be typing in the other. Before the backport the
constructor ran on the worker, so the second click's check usually saw the first window; the race
existed but was narrower. Bounded and self-evident when it happens: C.

**Fix shape:** move the guard inside the `invokeLater` so check-and-construct are atomic on the EDT;
the worker keeps the model reads (`toCSV` etc.) it was given the thread for.

### MB-C3. The comma message nobody can reach

`route.ui.errorCommaLoc` has zero references in `src/` - `refuseUnusableName` and its
`RouteCommand.isNameUsable` consolidation replaced the last one - but the key still sits in all
eight bundles. Dead data, one deletion per bundle, entirely optional before release.

## MB-D1. Clean checks and suspicions that died correctly

Each backported fix was read in its enforcing method on master, not in the diff:

- **Speed-zero guard** ([Layout.java:3174](../../src/org/traincontrol/automation/Layout.java)):
  placed before `configureAndLockPath`, so nothing is locked or commanded on a refused dispatch; the
  `a673bc7` Start-path twin skips the locomotive inside `runLocomotives`' forEach (a lambda `return`
  is a per-locomotive skip, matching the inactive-locomotive precedent above it). `BR-B1` is
  genuinely closed.
- **Runtime timer**: the OFF path only credits when `lastStartTime > 0` and zeroes it after, so
  repeated STOP broadcasts cannot double-credit, mirroring the repeated-GO guard under test. The
  speed>0 gating of the whole block is pre-existing semantics, untouched.
- **`RemoteDeviceCollection`**: all nine public methods are synchronized - no unsynchronized twin
  remains - and the corrected rationale (`a673bc7`) is accurate: the lock is a leaf; the methods
  touch nothing but the two maps.
- **Diagram click fix cannot lose a tile.** The suspicion was that `resetClipboard()` on a click
  might discard a cut tile; it dies on reading `initCopy`, which only records coordinates and a
  reference - deletion happens at paste time ("Delete after pasting instead"), so there is nothing
  to restore.
- **The address check does not block duplicated locomotives.** The suspicion was that `4adc7af`'s
  in-use check made the author's own duplicated-address workflow impossible; it dies on reading the
  call site - it is the informational "check duplicates" dialog, not a gate on adding. (Its keying
  is protocol-blind, matching the historical duplicate report - informational nuance only.)
- **`locIdCache`**: `volatile`, rebuilt under `synchronized` into a local and assigned whole, never
  re-nulled - the on-demand rebuild in the UDP reader can never see a partial map.
- **`isNameUsable`**: lowercase prefix constants match the `toLowerCase` comparison in
  `dedupKeyOf`; the three tests prove the rule rather than restate it, and the refused-import
  monitor test pins `newRoute`'s `disable()` with the precondition that makes it meaningful.
- **The case-only rename test** counts surviving files rather than asking by name, so it is
  meaningful on both case-sensitive and case-insensitive filesystems.
- **Readme encoding suspicion died on the bytes**: the three curly apostrophes in the 2.8.1
  changelog are valid UTF-8 (this reviewer's ANSI console read mangled the display, not the file).
  Every 2.8.1 changelog claim was checked against the enforcing code - including "needing the graph
  reloaded" for the callback fix, accurate because the wrapper deliberately leaves the path locked.
- **Wiring**: `RAW_VERSION` is 2.8.1; both new message keys are present in all eight bundles,
  byte-level ASCII-pure (English pending translation is the author's recorded decision in
  `ac66dc7`, not drift); all test classes including `testFeedback` are registered in `build.xml`.
- **Scope check**: `git diff` confirms the thirteen "Plan:" commits touch no `src/` or `test/`
  file, so this delta plus the `FV`/`RS`-validated 2026-08-02 state is the whole of v2.8.1.

## Dispositions, 2026-08-18

All four are addressed. Both branches were checked against every finding rather than master alone:

- **MB-B1 and MB-C1 were master-only.** The v3.0.0 branch already gathers the Lite repaint off the
  event thread and already routes every callback through one guarded door, which is the shape this
  review recommends; the backport brings master to the same place.
- **MB-C2 and MB-C3 were on both**, and are fixed on both.
- **One thing the review did not find, discovered while fixing MB-B1:** the branch gathers the path
  search off the event thread but still read `getTimetableStartingPoint` - synchronized on the same
  monitor, three times per repaint - on the EDT. Master had it too. Moving the search and leaving those
  would have left the stall in place while appearing to fix it, so the legend read is now gathered with
  the paths on both branches.

Nothing here has been run. A locomotive database is bound to the CS2 port on this machine, so every
model-based test class skips with "Address already in use". Both commits compile clean; the suite still
has to pass before the tag.

## Validation of the fixes (`68d78e4` on master, `0e3e280` on v3.0.0) - 2026-08-18

Validated by the reviewer who filed the findings, each fix read in the enforcing method on master;
the v3.0.0 copies of MB-C2/C3 checked for shape parity. Nothing was compiled or run by this pass
either - the suite gate in the release test plan stands.

- **`MB-B1` - correct, and the prescribed split exactly.** `findPaths()` gathers the path search and
  the timetable-start legend read off the event thread; `updateState(loc, found, haveFound)`
  consumes the finished snapshot on the EDT; the dispatch index is still resolved against the list
  the user saw, so `UH-B5`'s fix survives. Three details verified rather than assumed:
  `AutonomyRenderer` is a fixed pool of **one**, so gathers cannot race each other on the panel's
  gathered fields and applies arrive in order; the gathered fields cross threads through the
  `invokeLater` post, which is a happens-before edge; and a gather that throws only leaves that
  panel un-refreshed for one cycle. The disposition's bonus catch - the legend reads had stayed on
  the EDT on both branches - is real and correctly folded into the gather.

  **One bounded residual, recorded not re-filed.** `findPaths` answers null for a locomotive with no
  location, and `updateState` treats a null answer as "no gather" - so the panel of a locomotive
  that is in the run list but not on the graph still calls the synchronized `getPossiblePaths` on
  the EDT (a cheap no-match walk, but the monitor acquisition blocks under contention). Needs three
  conditions stacked: semi-autonomous multi-train operation, an arrival overlapping a configuration,
  and an unplaced locomotive in the run list. One-line close whenever convenient: have the apply
  treat `haveFound` with a null list as an empty list, or have `findPaths` return empty rather than
  null for the no-location case (the auto-running case needs no change - that branch never
  searches).

- **`MB-C1` - the code half is complete; the comment half was not done.** All seven `callback.apply`
  sites - dispatch, both milestone loops, both completion loops, and the two graph-refresh fires -
  now route through `fireCallback`, and there is nowhere left to fire one unguarded. Catching
  `Throwable` is defensible here for exactly the reason its comment gives. But the finding's first
  item is still open: the stale comment above the dispatch site still says a throw left "the wedged
  state that only reloading the graph clears", one screen above `fireCallback`'s javadoc saying,
  correctly, that the wrapper unwinds it to an abort - two authorities, disagreeing, adjacent. The
  outer try/catch at that site is also now unreachable, since `fireCallback` cannot throw. Both are
  comment-grade edits: delete the dead outer try/catch and the stale paragraph, and let
  `fireCallback`'s javadoc be the one account.

- **`MB-C2` - correct on both branches.** Check-and-construct are adjacent inside the `invokeLater`
  at both entry paths, so the EDT serialises them; a second click now finds the first editor and is
  told so. The model reads (`toCSV`, conditions) stayed on the worker, which is what that thread was
  for.

- **`MB-C3` - correct on both branches.** Zero references in `src/`; the key is gone from all eight
  bundles.

- **The process around the fixes held.** The commit and disposition say plainly that nothing was
  run and why; the release test plan (`2b0eef7`) is risk-ordered with the suite as item 0, names
  the configuration-failure skip trap that would make a red suite look green, and tests `MB-B1`
  hardest - including the specific regression its own fix shape could introduce. No `v2_8*` tag
  exists yet, which is the correct state until the suite passes.

**Verdict: all four findings are resolved in substance.** The two leftovers - the unplaced-locomotive
EDT fallback and the stale dispatch-site comment - are below release-blocking severity and are
recorded above with their one-line shapes; neither needs to gate the tag.

## The two leftovers, closed (`5f0a75e` on master) - 2026-08-18

- **The unplaced-locomotive fallback**: `haveFound` is now the only flag consulted - a null gather

  are gone, replaced by a pointer naming `fireCallback`'s javadoc as the single account; the

`5f0a75e` compiled clean and was not run (the CS2 port was in use by testing at the time), so the
