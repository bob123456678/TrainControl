# Review of the v2.8.1 backport delta

**Prefix for citing this document: `BR`.**

Reviewed at `4adc7af` on `master`, 2026-08-17 — the v2.8.1 release, being twelve fixes carried back
from `autonomy-diagram-r0` plus a version bump and changelog. Nothing was compiled or run.

## Scope and method

The fixes were **not** cherry-picked. Cherry-picking `11fabbb` conflicted in four places because its
diff context includes autonomy changes to `CS2File` that master does not have, so every fix was
instead re-applied to master's own files by a script matching the original text. Every patch matched
exactly — which proves the anchor matched, and nothing more. This pass existed to check the rest.

Five questions: is each fix correct in master's context, where the branch's autonomy work does not
exist; does it fix its `WP` finding judged against the failure scenario; does it introduce anything;
is each changelog entry a defect a real 2.8.0 user could have hit; and does anything in the delta
reference concepts master lacks.

**Verdict: the delta is sound.** No fix depends on branch-only code, every symbol resolves on master
including the reused message key in all ten bundles, and no compile error was found. One fix was
incomplete against its own finding, identically on both branches.

## B - Medium

| B1 | The speed-0 guard never reached the full-autonomy Start path | **Fixed 2026-08-17** (`a673bc7`) |

### B1. The speed guard was placed where Start does not go

`automation/Layout.java` - `runLocomotives` calls `runLocomotive(loc, loc.getPreferredSpeed())`, and
`runLocomotive` throws for a speed below 1 long before any path reaches `executePathInternal`, where
the guard was added. The catch answers by calling `invalidate(...)` and `stopLocomotives()`.

So the consequence that mattered most in `WP-B1` - one locomotive placed without a speed ever being
chosen turning Start into "configuration invalid, must reload", stopping every other locomotive - was
untouched by the fix that closed the finding. The two semi-autonomous dispatch paths and the
timetable path were genuinely fixed.

This is the cycle's most repeated mistake in its purest form: a guard added at one call site, its twin
left alone, and the finding marked Fixed. It was identical on the branch, so `WP-B1`'s disposition
overstated on both sides until `a673bc7`. The changelog entry claimed only the dispatch consequence
and so was accurate throughout.

Fixed by refusing the locomotive in `runLocomotives` itself - skipped exactly as an inactive
locomotive already is - so the rest keep running.

## C - Low

| | Finding | Status |
|---|---|---|
| C1 | Crash window between the two moves of a case-only rename | Open |
| C2 | The recorded rationale for synchronizing the device collection was false | **Fixed 2026-08-17** (`a673bc7`) |
| C3 | A 0-speed locomotive in a parallel timetable retries in an unbounded paced loop | Open |

**C1.** `base/LayoutDiagram.java` - if the process dies between `move(original, staged)` and
`move(staged, newFilePath)`, the page exists only as `<name>.cs2.renaming`, which nothing loads:
pages are opened by index-name plus `.cs2` and no code scans the directory. The bytes survive and the
window is milliseconds. A leftover staged file also makes the next case-rename of that name fail with
`FileAlreadyExistsException`, which is caught and surfaced as the normal error dialog - annoying, not
lossy. Left open deliberately; closing it properly means a recovery scan at load, which is more
machinery than the risk justifies.

**C2.** The comment added with the fix said `RemoteDeviceCollection` had to stay `HashMap`-backed
because the class is `Serializable` and its fields are written into `LocDB.data`. That is false:
`saveState` persists `MarklinSimpleComponent` snapshots, nothing serializes this class, and the
`Serializable` declaration is vestigial. The synchronized design is right for a different reason -
`add()` must change both maps together, which per-map atomicity cannot give - and the comment now
says that, and records what it used to claim. A confidently wrong rationale is worse than none, which
is this folder's own rule.

**C3.** `automation/Layout.java` - the new guard makes `executePath` return false, and the
non-sequential timetable branch has no attempt ceiling, so a 0-speed locomotive now loops at
`pacedWait` cadence logging two lines per attempt. Strictly better than the old parked thread with
`isRunning()` stuck true - the run can be stopped, and sequential mode aborts after
`STAGING_MAX_ATTEMPTS` - but it is an unbounded log loop somebody has to notice. Largely mooted by
`B1`'s fix, which stops such a locomotive being started at all.

## D - Not defects, and checks that came back clean

- **The synchronized collection introduces no deadlock.** Every method touches only the two maps,
  whose keys are `String`/`Integer` - no user `equals`/`hashCode`, no wait, no I/O, no call-outs - and
  the one internal call (`delete` to `hasName`) is same-lock reentrant. The lock is strictly a leaf,
  so no ordering cycle is constructible. The heaviest caller, the GO/STOP broadcast handler, takes
  `getItems()` and releases before touching any `speedMonitor`. `WP-B4`'s sharp end is closed because
  `saveState` iterates the copies `getItems()` returns.
- **The palette still arms and places.** `LayoutGrid.getValueAt` returns null for (-1,-1), so the new
  early return fires exactly on palette releases; `mouseClicked` then re-arms, and placement happens
  through `receiveClickEvent` on the grid square - `beginDrag` is a no-op on empty squares, so
  `endDrag` never intercepts the placement click. The same-square `resetClipboard()` ends in the same
  state as before the fix, minus the forged undo entry.
- **The two `RouteEditor` EDT moves read nothing stale.** Nothing reads `routeEditor` after the
  `invokeLater` in either thread body; the capture path now reads and writes it on the EDT only, so
  the change removes a race rather than adding one.
- **The derived duplicate map cannot be corrupted.** `getLocAddresses` builds a fresh map per call and
  `getDuplicateLocAddresses` filters its own copy - no aliasing across callers.
- **`disable()` retires the rejected monitor and cannot hit a live route.** The monitor rechecks
  `enabled` after the feedback wait and before firing, and both `newRoute` call sites pass freshly
  constructed objects, never a database resident.
- **The remaining fixes check out against their scenarios**, including `WP-A3`'s line shapes
  enumerated exhaustively (route-trigger lines carry no comma; feedback lines key per sensor;
  accessory dedup and last-write ordering preserved and pinned by the third test).
- **The changelog is accurate.** Twelve entries for eleven fixes; `WP-B9` deliberately has none. The
  least obvious claim - that clicking a diagram accessory also discarded runtime - is supported:
  `LayoutLabel` calls `go()` when the model believes power is off while `Locomotive.powerState`
  defaults true, making that GO locomotive-redundant, and GO reaches every locomotive.

## What this pass missed

**Nothing was compiled**, so "no compile errors" rests on symbol-by-symbol reading.

**The branch and master were not byte-compared** beyond a spot check of `Layout.java`; correctness was
verified on master directly instead. The two copies of the `RemoteDeviceCollection` class comment have
since diverged in wording, though not in content.

**Not covered:** the accuracy of translated strings in the nine non-English bundles (existence only);
CS2/CS3 wire behaviour; macOS `Files.move` case semantics, where Windows reasoning was verified and
macOS assumed alike; and `LayoutEditor`'s keyboard-paste and bulk row/column tools beyond confirming
they do not route through `endDrag`.
