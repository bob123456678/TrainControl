### SVT-B1 - the exit test is green without the exit fix

`testTheExitKnowsTheRouteEditorHasUnsavedWork` (`testLayoutTiles.java`, UIX-B1) asserts `editor.hasUnsavedWork()` and `ui.routeEditorHasUnsavedWork()` on both sides of `appendCommand`.  Both are new seams: `hasUnsavedWork` is the expression `closeIfThrowingNothingAway` always had (`!locked && !stateSignature().equals(loadedSignature)`) extracted; `routeEditorHasUnsavedWork` is `routeEditor != null && isDisplayable() && hasUnsavedWork()`.  The FIX is one `if` in `WindowClosed` (`TrainControlUI.java:19153-19156`) calling `routeEditor.maySettleBeforeExit()`.  Delete that `if` and every assertion in this test still holds, because nothing in the test reaches `WindowClosed`, and cannot - it ends in `System.exit(0)`.

So the test names a regression ("the exit does not know the route editor is holding unsaved work, so it exits without asking") that it cannot catch.  The javadoc is honest about it ("what is asked here is the predicate it is built on ... the dialog itself is MT-458" - which is also the wrong tag; MT-461 is the exit test, MT-458 is the negative maximum), but a test in the battery reads as protection whatever its javadoc says, and this one protects a predicate that was never wrong.  The same reasoning shows the record's claim is not plausible: MT-461 says the finding was fixed "with a test seen failing first", and against the old code this test does not compile (`hasUnsavedWork`, `routeEditorHasUnsavedWork` did not exist); against the seams with the `if` absent it is green.  There is no version of the code this test is red against except one where `stateSignature` itself is broken.

**What to change.**  Pin the call site.  The cheapest real pin follows a pattern the window already has (UIX-D8 counts three `answeredByATest` hooks): split the pre-exit half of `WindowClosed` - the layout-editor question and the route-editor question, everything before the autonomy stop and `saveState` - into a package-visible `boolean mayExitNow()`, and give `RouteEditorFrame.maySettleBeforeExit` an `answeredByATest` hook so the dialog can be answered without a person.  Then the test opens the editor, types, sets the hook to No, and asserts `mayExitNow()` is false; with the hook at Yes, true; with nothing typed, true without the hook being consulted.  That is red with the `if` deleted.  Failing that, the fallback the repository already uses for unrunnable handlers is a source-shape census in `regression` asserting `WindowClosed` contains `routeEditor.maySettleBeforeExit()` before its `System.exit` - weaker (a guard knows only what it lists) but it does go red on the mutation the current test cannot see.  Either way, correct the javadoc's `MT-458` to `MT-461`, and take "seen failing first" off MT-461's *What this is* line in a dated Comment, since rule 5 forbids editing the line.

### SVT-B2 - the accessory-highlight seam never goes back to false, so the second half of the highlight test is guarded by nothing it states

`LayoutLabel.accessoryHighlight` (`LayoutLabel.java:1040-1052`) is set when the 2.25 s highlight goes up and cleared ONLY by `endAccessoryHighlight()`.  The timer's own action (`:1042-1049`) puts `lastIcon` back and leaves the field set.  So `isAccessoryHighlightOutstanding()` - whose javadoc says "true while the yellow wash ... will still be taken off by its own timer" - answers true for the rest of the label's life after its first highlight, and `awaitHighlight` returns at once whenever a highlight has EVER been up on that label.

Trace the test with that in hand.  `warmedSignalLabel()` runs one highlight and sleeps 2600 ms: the timer fires, the field stays set.  Case ONE: `flashHighlight()` calls `endAccessoryHighlight()`, which nulls it, so the later `awaitHighlight` genuinely waits for the new highlight - fine.  Case TWO: `second = warmedSignalLabel()` leaves the field stale-true; `invokeAndWait(updateImage(true))` only queues `setImageOnEDT` (the image key is cached, so `setImage` posts with `invokeLater` and returns); `awaitHighlight(second)` returns true immediately on the stale field, before the queued highlight has landed; the test then calls `invokeAndWait(flashHighlight)`.  What saves it today is EDT ordering: the queued `setImageOnEDT` runs before the flash runnable, so the highlight IS up when the flash captures, and the assertion is exercised in the order the test claims.  But nothing in the test says so, the "precondition" cannot fail, and the wait is not a wait.  Two consequences:

- If the highlight branch ever stops firing on this fixture (`hadIcon`, `CLICK_TIMEOUT`, `edit`, a changed image key so the load goes to the worker and lands AFTER the flash), case TWO passes anyway: `endAccessoryHighlight` nulls the stale field, `assertFalse(isAccessoryHighlightOutstanding())` holds, and the test reports the flash-over-highlight order protected when it never happened.  That is the SOP's "passed while exercising only the cases that never needed fixing".
- If the image key is NOT cached when `updateImage(true)` is called - a fresh `size`/`edit` key, or a cache cleared by another test in the same JVM - `setImage` goes to `tileImageLoader` and the highlight lands on a worker's schedule, possibly between the flash and the assertions; `discardFlash()` then makes `assertTrue(second.isFlashOutstanding())` fail at random.  Today the key is cached by `drawnSignalLabel`'s own load, so this is a latent shape rather than a live one, but the test is one refactor of `setImage` away from it.

Also: the test thread polls `flashTimer`/`accessoryHighlight` (non-volatile, written on the EDT) from outside the EDT in `awaitHighlight` and `awaitIconChange`; `Thread.sleep` in the loop makes this work on every JVM in practice, and it is noted rather than counted.  `awaitIconChange` is unused.

**What to change.**  (1) In the timer's action, after `this.setIcon(lastIcon)`, set `accessoryHighlight = null` - the seam then means what its javadoc says, and `endAccessoryHighlight` stops doing a redundant `setIcon` on every flash.  (2) Make `awaitHighlight` wait for a highlight that STARTED after the call: a `private int highlightsStarted` incremented where the timer is created, read through a package-visible getter; `awaitHighlight` takes the count before `updateImage` and waits for it to rise.  Case TWO then waits for the highlight this `updateImage` started and only then flashes, whatever thread the image arrives on.  (3) Delete `awaitIconChange`.  With (1) and (2) the precondition in case TWO can fail, and the UIX-B2 mutation (drop `endAccessoryHighlight()` from `flashHighlight`) is red for the reason the test names rather than for a stale field.

### SVT-B3 - the mid-run delete rides on a fixed sleep

`testARouteFinishesWhenItsLocomotiveIsDeletedMidRun` waits (bounded, 5 s) for `isExecuting()`, then `Thread.sleep(400)`, then asserts `0 < accessories < 8` as the precondition that the delete lands mid-route.  The upper bound is safe: each command is followed by `SLEEP_INTERVAL + max(delay, DEFAULT_SLEEP_MS)` = 50 + 150 = 200 ms (`MarklinRoute.java:1060`, `MarklinControlStation.SLEEP_INTERVAL = 50`, `DEFAULT_SLEEP_MS = 150`), so seven commands need 1.4 s.  The lower bound is a race: between `setExecuting()` and the first accessory frame the route thread logs, calls `updateTiles`, `hasEmergencyStop`, and `heldReason` for the first command (which asks `isAutonomyRunning` -> `hasAutoLayout`), and then sends.  On an idle machine that is milliseconds; in a battery that has just opened a real window, with the tile image loader and the EDT busy, 400 ms is not a guarantee, and when it is missed the test fails with "0 of 8 commands had been sent" - honestly, but at random, which the SOP counts as worse than no test.

**What to change.**  Replace the sleep with a bounded poll: wait up to 5 s for `accessories.get() >= 1`, then assert `accessories.get() < 8` (still guaranteed by the 200 ms floor - the poll returns within one command of the first frame).  Keep the message.  The 15 s wait for the route to finish is already bounded and fine.
