# Review of the layout-test round and the two features — 2026-08-22

One Opus reviewer, asked for regressions and incompleteness across the seven commits from the hover fix
through LT-F2. It found eight things worth acting on and confirmed six that were fine. Everything below
is either fixed and committed, or listed at the bottom as something for Adam to decide.

Prefix: **FR** (F-round review). Severity follows `docs/reviews/README.md`: A is data loss or a crash,
B is wrong behaviour a user will hit, C is a corner, D is cosmetic or maintainability.

### FR-A1 — the same wiring gap, twice

The one that matters. LT-A8 made a bulk column move carry the setup, and it did - except that the loop
which clears the line being vacated calls `delete()` on each square, and `delete()` announces to the
setup that the track there is gone, which drops that square's caption **and every caption elsewhere
naming it**, and writes that to disk. All of that happened before `applyBulkPlan` ran. So a moved column
arrived with its stations, names, lengths, facings and pairings intact and with **no station names
anywhere** - the empty placeholder, which is precisely the symptom LT-A9 was written to cure for single
tiles.

`delete()` now takes a `tellAutonomy` flag and the bulk loops pass false: the setup is told once, by
`applyBulkPlan`, which is the only thing that knows the difference between a square being destroyed and
a square being vacated.

This is the second time in three days that a fix has been correct and un-called. The first was LT-A8
itself. Both live in the one line of `executeTool` that no test can see, which is the gap named at the
bottom of `testLayoutEditorBulkEdits` - and it has now cost two defects. **Manual test 44 is the only
thing that covers it.**

### FR-A2 — switching asks a better question than closing

`leaveFor` reused `mayLeave()`, which discards unsaved setup edits when the user says yes. That is right
for closing, where the window is going whatever happens and the only question is whether the work goes
with it. It is wrong for switching, where the window comes straight back - and the default button was
Yes, so an hour of setup was one keystroke from being reloaded away by clicking a page tab.

The spec said "prompt for save/discard", and both modes do have a save, so switching now offers three
answers: **Save and Continue**, **Discard and Continue**, **Stay Here**, defaulting to Save. Closing
still offers two, because closing cannot offer to come back.

### FR-B1 — the sweep LT-A8 did not finish

`pasteSelection`, `fillSelection` and a single-tile copy all wrote a tile over an occupied square and
told the setup only about the caption. Everything else - the station designation, the name, the length,
the facings, the arrival restrictions, the link name, the pairing, the switched-off flag - stayed on a
square whose sensor had just been replaced. Reconcile cannot find those, because it drops settings from
squares that are EMPTY and these are occupied, just by something else.

Plainest reproduction, which is why this is a B and not a C: arm a piece of plain track from the palette
and click a set-up station. All three now call `forgetTiles` on the square they land on.

### FR-C3 — "its station is moving" is not the rule

The label-sparing rule was described as "when the thing it refers to is what has just built over it" and
implemented as "the thing it refers to is moving anywhere". Those differ the moment more than one tile
moves at once - which is every column move, where a destination column twenty squares long contains a
label naming one of the arriving tiles roughly as often as not. The loose rule left that name drawn over
whichever other tile actually landed there.

Fixing it exposed that one of my own tests encoded the loose behaviour: a group drag where Platform4
lands on Platform3's label was asserting that the label survives, which would draw one platform's name
across the other's track. That test is now two, one for each side of the real rule, and the loose rule
fails both.

### FR-C1 and FR-C2 — a preference is a record of an answer

`LAST_EDITOR_AUTONOMY_PREF` was written on every open, including when the mode had been forced back to
the track because trains happened to be running, and including on incidental jumps - a double-click on a
train's name, a finding, the walk to a link's other end. Work in the setup editor for a week, start a
train, press Edit once, and the preference said "track" forever.

It is now written only when the user has actually named a mode: the Autonomy menu's own item, and the
sidebar's mode tabs. Not from a fallback, and not from a glance.

## Confirmed sound

The reviewer checked and cleared these, which is worth recording because they were the risky parts:

- **The content-pane wrap is complete.** Every `getContentPane()` in the tree was checked, including
  `PositionAwareJFrame`, the drag ghost window, and the GEN block that runs before the capture. The
  three redirected casts are all of them.
- **`mountSidebar()` cannot be built in the wrong mode.** `render()` only queues; `setAutonomyMode`
  runs synchronously before the queued body reaches it. Both reopen paths re-enter through the same
  method and inherit the same ordering.
- **The `editLayoutButton` protocol holds on both reopen paths**, and `layout.setEdit(false)` is
  correctly present in the autonomy branch and correctly absent in the track one.
- **`mayLeave()` is a faithful extraction** of the old `confirmExit()`, statement by statement.
- **`getAutonomySession()` vs `editableAutonomySession()`** is right at every site - the distinction
  between what can be opened and what can be defaulted to.
- **No non-ASCII crept into any bundle.**
