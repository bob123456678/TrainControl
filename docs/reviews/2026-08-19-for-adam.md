# What to look at when you're back

In order. Roughly two hours if you do all of it; the first three are the ones that matter.

---

## 1. Run the thing (30 min)

Nothing below substitutes for this, and there is one thing I could not test at all.

Open a layout, add a configuration, place two trains, press start. Then:

- [ ] **Hover "No available paths"** on a locomotive that cannot move. You should get a list of
      stations and, for each, why. This is new and it is the feature I would most like your read on.
- [ ] **Open the setup editor and press "Why is it not moving?"**, then click a square with a train
      on it. Routes it *could* take are drawn on the track; reasons for the rest are listed. If you
      have unsaved edits it says so; if not, it says nothing.
- [ ] **Multi-select**: shift-click a few squares, shift-drag a box, right-click → Selection → *Select
      This Whole Row*. Drag the group. Fill it. Delete it. Undo — each should be **one** step.
- [ ] **The new route editor**: Routes menu → the new editor. Open an existing route, change nothing,
      save. Then check the route still has its delays and its decoder types. Two separate data-loss
      bugs lived exactly there.

> **The one thing I could not test:** anything involving a real Central Station. `testAutoDetect` has
> failed all session because nothing answers on the network. The sync work is covered by a mock
> station, which is not the same as your CS3.

## 4a. One behaviour change you will feel (1 min)

**A graceful stop now takes slightly longer to report itself finished** - and it is telling the truth
for the first time.

`isRunning()` was "the flag, or somebody is on a path". A locomotive thread passes its `while
(running)` check, then spends time in `pickPath` - a shuffle, a sort and a search of the whole graph -
and only joins `activeLocomotives` when it actually departs. In that window a train is about to move
and nothing could see it, so the layout reported itself stopped while a train was one instruction from
leaving. `moveLocomotive` would have accepted an edit; the interface would have re-enabled everything.

Live locomotive threads are counted now. The visible effect is that Start and the rest come back a
moment later after a Graceful Stop - when the run has genuinely finished rather than when it looks
like it has.

If it feels SLOW rather than a moment, tell me: the pacing delay between paths is skipped once a stop
is asked for, so the wait should be the last train arriving and nothing more.

## 5. Things I changed that you might disagree with (5 min)

Each is defensible and each is reversible.

- **Nine entries removed from the 3.0.0 changelog** as bugs that only ever existed on this branch. The
  judgement call is *"trains stopped moving even though routes were available"* — a lock-edge fault
  that only fires when one sensor is shared by several places, which is the derived graph's doing.
- **`Automation.md` split**: the user guide keeps that name, the JSON and API reference moved to
  `AutomationAPI.md`. Readme links updated.
- **Removed from the diagram editor**: paste-entire-row, paste-entire-column, the four
  shift-the-whole-diagram items and their methods, and `Shift+C`/`Shift+R`. Multi-select replaces
  them.
- **The condition editor now offers only accessory and feedback kinds.** The others produce a
  permanently false condition. Auto-locomotive is evaluated by routes but has no controls, so an
  existing one is preserved read-only.
