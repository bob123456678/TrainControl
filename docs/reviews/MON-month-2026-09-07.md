diagram-autonomy plan (2026-08-01) started turning into code; by the end of 2026-08-16 - two days -

## MON-A1 - `arrivedFrom` has two vocabularies, and only one of them blocks track

**Severity A - the covered-track protection Adam asked for on 2026-09-07 can be silently absent for
exactly the trains an operator described by hand. Mechanism confirmed at every site; what would
seal it is a ten-minute fixture, described below.**

The tail walk (`Layout.edgesCoveredByStandingTrains`, `src/org/traincontrol/automation/Layout.java`)
picks the first hop by matching the recorded side against geometry:

```java
if (standingHere.getArrivedFrom().equalsIgnoreCase(sideTowards(here, other)))   // Layout.java:5492
...
// Recorded, but naming a side no track leaves by - a stale value after an edit.
// Nothing can be said, and guessing would block the wrong rail.
if (segment == null) break;                                                     // Layout.java:5503
```

`sideTowards` (`Layout.java:5590`) is "the sign of the larger coordinate difference" **between
Points** - and Points sit at sensor tiles, often several tiles apart, so on any stretch that bends,
the direction of the neighbouring Point is not the side the metal leaves the square by.

There are three writers of `arrivedFrom`:

1. **The runtime**, on arrival (`Layout.java:6585`): writes `sideTowards(...)`. Geometric. Always
   matches the walk. Correct.
2. **The editor's "Train arrived from" menu** (`AutonomyEditorPanel.buildArrivedFromMenu`,
   `:2923`): offers `session.arrivalSides(target)` - the build's split sides - with a comment that
   states the divergence in so many words: *"THE BUILD'S SIDES (issue 5, 2026-09-07). The geometric
   form answers with the direction of the neighbouring POINT, which on a curve is not the side the
   metal leaves by."* It writes the chosen build-side string straight into
   `Point.setArrivedFrom(side)`.
3. **The placement prompt** (`ArrivalSidePrompt`, the "asked, assumed, forced" flow from
   `31ca168e`): same source, `sidesOf(session.arrivalSides(...))`. Same vocabulary.

Both vocabularies use the same four tokens N/E/S/W, so nothing can notice the mismatch - the value
is well-formed, it is just the answer to a different question. When the build side and the
geometric side differ (a berth whose first stretch behind it bends), the walk's first-hop match
fails, hits the `break` above, and blocks **nothing** - the comment at the break site even
documents the silent outcome, for a different cause ("a stale value after an edit"). The greying is
fed by the same walk (`AutonomySession.tilesCoveredByStandingTrains`), so the operator who looks
will see nothing grey; the operator who trusts their answer has no protection and no message.

Two things make this an A rather than a curiosity:

- The straight-fixture monoculture (MON-C17, and `8f006b3a`'s own admission about the tail tests)
  means every existing tail test has `sideTowards` == build side by construction. This divergence
  is only visible on bent geometry, which no hand-built graph fixture has.
- `sideTowards`'s own javadoc claims *"the same vocabulary `arrivedFrom` is recorded in"*
  (`Layout.java:5578-5579`) - true of writer 1, false of writers 2 and 3, which were added the same
  day. That sentence is how the next person will convince themselves this is fine.

**What would confirm it:** a fixture with Points at coordinates (0,0) and (2,1) joined by an edge
whose metal leaves the berth southward (build arrival side S); place a measured train, set
`arrivedFrom` = "S" through `setArrivedFrom` as the menu does; assert
`edgesCoveredByStandingTrains()` is non-empty. Run the same with the runtime-recorded value to see
the pair diverge. (Not run - this review does not touch the harness.)

**Fix direction, for whoever picks it up:** one vocabulary at the boundary - either the operator
doors translate the build side to the geometric side before storing (they know the tile and its
ports), or the walk matches against both spellings. The first is smaller and keeps the walk's
"recorded in one vocabulary" contract true.

## MON-B1 - The dash is a copy with two limbs missing, and its guard cannot tell

**Severity B - the commands panel offers a parking berth as if autonomy might choose it. Display
only: no train moves wrongly, but the display exists to predict what autonomy will do, and for the
exact case it was written for, it predicts wrongly.**

`AutoLocomotiveStatus.notChosenByAutonomy` (`src/org/traincontrol/gui/AutoLocomotiveStatus.java:148-154`):

```java
return (p.isReversing() && p.isDestination())
    || (loc != null && p.isTerminus() && !loc.isReversible())
    || p.getExcludedLocs().contains(loc) ? " -" : "";
```

The rule it copies - `Layout.barredFromAutonomy` (`Layout.java:4320-4348`) - has five limbs. The
copy has three. Missing: `!isAutoDestination()` and `!isActive()`. The javadoc above the copy says
the copy is deliberate (lock-free, EDT, three times per repaint - fair) and that
`testTheDashAgreesWithTheRule` "is what keeps it honest". It does not:

- `test/core/testWhyStuck.java:300` exercises **only the terminus limb** (`setTerminus(true)` +
  `setReversible(false)`), while claiming *"MUTATION this catches: removing any limb of the dash's
  predicate"*. It cannot catch the absence of a limb that was never there.
- The test directly above it (`testAStationBarredFromAutonomySaysSoRatherThanThatItIsBusy`,
  `:257`) even constructs the failing case - `setAutoDestination(false)` - and then compares only
  the model's answer, never the dash.

A modern parking berth is spelled `autoDestination:false` (`AutonomyBuilder.java:1004` emits it,
`Layout.parseAuto` reads it, `barredFromAutonomy` bars on it at `Layout.java:4326`). The dash's own
javadoc names *"a parking berth, which autonomy no longer chooses"* as its purpose; the predicate
only matches the legacy spelling (`reversing` + `destination`). This is the same shape as SVN-C4,
which this class already paid for once ("`280ff08b` moved that rule ... and this fourth mirror was
missed").

**Fix:** add the two limbs; extend `testTheDashAgreesWithTheRule` to sweep all five limbs against
`barredFromAutonomy` (the sibling test already shows how to build each case), or better, iterate
the cases and compare the two answers wholesale.

---


**Fixed 2026-09-07.** Both limbs added, in the rule's order. The guard was rewritten first and
seen red on `!isActive()`: it now iterates every case - switched off, a modern parking berth, a
reversing station, a terminus this train cannot back into, an exclusion, and one clean control -
and compares the dash's answer with `barredFromAutonomy`'s wholesale, both reached by reflection.
Asserting the two agree is what a copy needs; asserting a mark is what let two limbs go missing.

## MON-B3 - The intent document argues with itself, and misdescribes one mechanism

**Severity B - not code, but on 2026-09-07 Adam made `behaviour.md` the documented intended
functionality, with disagreement between it and the code defined as a bug for him to rule on. A
self-contradiction in that document is a spec defect: both sides of it can cite the spec.**

Two confirmed instances:

1. **§3 states a rule in bold and retracts it seven lines later without deleting it.** Line 136:
   *"A manual journey that needs a turn the operator declined is refused before it starts, naming
   the square."* Line 147-151: that ruling *"dissolved the refusal described above"*; *"No journey
   is refused on the operator's answer any more, and none can be."* The code agrees with the
   retraction (`d45d7951` removed the mechanism; no refusal message key exists in any bundle). A

   justification - gets the wrong answer to a question Adam personally ruled on.

2. **§3's mechanism description is the opposite of the code.** Lines 176-179 say the mid-run
   baseline "is brought up to date as it arrives" and that it *"used to be recorded with
   `putIfAbsent`"*. `TrainControlUI.java:10219` still reads `lastSeenDirection.putIfAbsent(...)`,
   with a comment giving the opposite rationale ("overwriting an existing baseline here is exactly
   what was swallowing the change"); the levelling happens later and elsewhere
   (`reconcileFacingWhenIdle`, `:6171`), on the next idle refresh, not on arrival. The *outcome*
   the document describes is real; the stated mechanism and tense are both wrong - and this is the
   precise mechanism REG8-B1/IND9-B6 (still open, "needs a run") are about, so the wrong
   description points any future debugger of that window at the wrong code.

(REG8-C1 flagged two other self-contradictions in the same sections on 2026-09-07 and `8b4531ec`
settled those; instance 1 above is a third, and it survived that sweep. Checked at HEAD.)

**Fix:** delete the retracted bolded rule (the retraction paragraph can carry the history), and
rewrite lines 176-179 to name `reconcileFacingWhenIdle` and the idle refresh.

## MON-B4 - The reversal dialog describes the withdrawn question

**Severity B - every operator answering the month's most-reworked question is told it is about the
wrong kind of square, in all eight languages.**

`src/org/traincontrol/resources/messages.properties:306`:

> `autolayout.ui.confirmManualReversal={0} will pass {1} on its way, where trains may turn
> round.\n\nKeep its current direction?`

Since `d45d7951` ("Only the destination is asked about") the prompt is only ever raised about the
**destination** - `ManualReversalPrompt.java:108-113` passes `path.get(path.size() - 1).getEnd()`
and nothing else, and the old first-may-turn-square fallback is gone (`:98` records its removal as
the source of REG7-A1). The train does not "pass" the square in question; it stops there. All
seven translations carry the same "passes through on the way" sense (de: "fährt unterwegs über
{1}", fr: "passera par {1} en chemin", pl: "będzie przejeżdżać przez {1} po drodze", ...).

The yes/no semantics are unaffected - "Keep its current direction?" is still the question - so no
wrong click follows *necessarily*; but the preamble is the operator's only explanation of why they
are being asked, and it describes the behaviour that was removed because it drove trains off their
paths.

**Fix:** reword to arrival ("will arrive at {1}, where trains may turn round"), 8 bundles.
