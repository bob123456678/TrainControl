### MKR-B1 - the diagram runs the route it was wired with, not the route in the database

| | |
|---|---|
| **Disposition** | Open |
| **Introduced** | before 2.7.4c for the Central-Station-as-source configuration and for the sync's own re-read (`v2_7_4c:MarklinControlStation.java:433-440` binds the same way, `v2_7_4c:LayoutDiagramComponent.java:168` executes the bound object); **widened by this delta** for the local-folder configuration: at 2.7.4c the delete-route door ran `syncWithCS2()`, which under a local folder cleared and re-wired every page (`v2_7_4c:MarklinControlStation.java:772-774`), and `d8d1ea50` (OB-155) took that sync away for local route ids without putting a re-wire in its place |
| **Sibling** | CS3-B2 is the same shape for an accessory - a tile bound to an object the database evicted - and is accepted.  This one is different in what it costs: an accessory tile bound to a stale object shows the wrong position; a route tile bound to a stale object SENDS the wrong commands |

**The binding.**  `wireComponents` (`:756-765`) resolves a route tile once, `MarklinRoute r = this.routeDB.getById(c.getAddress())`, and stores the object on the component, `c.setRoute(r)` (`:765`; `LayoutDiagramComponent.setRoute`, `:650`).  A click on that tile ends in `LayoutDiagramComponent.execSwitching` (`:179-185`), which calls `this.route.execRoute(false)` on the STORED object - not `network.execRoute(name)` and not a lookup by id.  Both doors in `LayoutLabel` (gui) reach it: `:646` after the conflict question and `:684` on the plain path; the conflict question itself is asked of the stored object (`:534-535`), and right-click Edit passes the stored object's name (`:366`).  `LayoutGrid` (gui, `:1867-1869`) registers the label on the stored object too, `c.getRoute().addTile(...)`, so the stored object is also the only one whose `updateTiles()` (`MarklinRoute:275-288`) can highlight the tile.

**What replaces the object.**  The route database never edits a `MarklinRoute` in place; it swaps it:

- `editRoute` (`:1957-2034`): `deleteRoute(name)` at `:2010`, then `newRoute(trimmedNewName, id, ...)` at `:2012`, which constructs a new `MarklinRoute` (`:2180`).  Reached by the route editor's Save (`RouteEditorFrame:2798`), by Enable/Disable Automatic Execution (`TrainControlUI.writeRouteEnabledState`, `:21458`, called from `enableOrDisableRoute` `:21409` and `BulkEnableOrDisable` `:21390`).
- `syncWithCS2` (`:1449-1502`): a station route whose commands, sensor, trigger or conditions differ from the copy in hand is deleted at `:1478` and re-added at `:1484`; a same-name-different-id route is deleted at `:1460`.  Reached at every start-up (constructor `:482`), from the Sync button, and automatically after enable/disable, bulk enable/disable, a non-local route delete and a JSON import.
- `importRoutes` (`:3977-3998`): deletes EVERY route and re-adds from the file.
- `deleteRoute` (`:3517-3540`) on its own: `disable()`, strip from the autonomy selection, `routeDB.delete` - the tile keeps the object, now in no database.

**What re-binds, and when.**  Only `wireComponents`, and only from `syncLayouts` (`:874`).  `syncLayouts` runs from `syncLayoutsFromConfiguredSource` (`:537-593`), which under a local layout folder re-parses on every call but with the Central Station as the source re-parses ONLY when `layoutDB` is empty (`:587-590`).  So:

- **Central Station as the diagram source**: pages are wired once per session - by the constructor's sync, or by Switch to CS Layout, which clears first (`TrainControlUI:22272`).  `refreshLayouts()` (`:604-618`), which every editing door calls through `layoutEditingComplete` (`TrainControlUI:23168-23210`), is a no-op.  Nothing re-binds a route tile for the rest of the session.
- **Local folder as the source**: `refreshLayouts()` re-wires, but only the doors that call it do - a diagram edit and the route editor's Save (`RouteEditorFrame:2812`).  The delete-route door (`TrainControlUI:19361-19382`: `deleteRoute`, `refreshRouteList`, a sync only when the id is a station one, `repaintLayout`), enable/disable (`:21409-21416`), bulk enable/disable (`:21400-21405`) and JSON import (`:25412-25418`) never call it.  And the sync wires BEFORE it re-adds - `syncLayoutsFromConfiguredSource()` at `:1428`, the route loop from `:1449` - so a sync's own re-read always leaves the tile on the old object, whichever source is configured.

**The caller path that needs no coincidence.**  Route page, right-click a route that is drawn as a tile, Delete, confirm.  With the Central Station as the source, or with a local folder and a route id at or above 1000, the tile is now bound to an object that `disable()` has been called on and that no database holds.  Click the tile: `execSwitching` -> `execRoute(false)` -> the route thread starts (`MarklinRoute:601`), `setExecuting()` succeeds (the flag is on the object, not the database), and every accessory command in the deleted route goes out through `network.setAccessoryState` (`:864`).  `network.getRoute(name)` is never consulted for the route itself - only for a chained route (`:978`).  Nothing checks `enabled`; manual execution never has (behaviour.md section 7a, "a route tile on the diagram all run the route whatever its conditions say").

**The caller path on Adam's railway.**  His pages draw station routes as tiles - `cs2_sample_layout/config/gleisbilder/1 - Main.cs2` has twenty `fahrstrasse` tiles with `.artikel` 1 to 58, and `test/layouts/live-snapshot` the same set.  Change any of those routes on the Central Station - add a turnout, re-order it - and either press Sync or restart TrainControl.  On restart the sequence is: `restoreState` rebuilds the route from `LocDB.data` with LAST session's commands (`:476`), the constructor's sync wires every tile to that object (`:482` -> `:1428` -> `:874`), and the same sync then finds the station's copy differs (`RouteCommand.equals`, `:401`, compares type and the whole config map) and replaces it (`:1478`, `:1484`).  For the rest of that session the tile runs last session's route and the play button on the route page runs this session's.  `saveState` on exit writes the new copy, so the NEXT start is consistent - which is what makes this hard to notice: it is one session per station-side edit, and the session in which the operator is most likely to press the tile to try the change they just made.

**What goes wrong on the railway.**  (1) The tile sets the ironwork of a route the operator changed or deleted, with the log reporting the route by name as executing and executed exactly as if it were current.  (2) A route run from the route page or by its s88 trigger - the NEW object - highlights nothing on the diagram, because no label is registered on it; the highlight for a tile click appears, because that is the old object's registration.  (3) After a rename in the route editor, right-click Edit on the tile calls `editRoute` with the old name and gets "route does not exist".  (4) `runningRouteDriving` (`:3271-3283`, CS3-B1's door) walks the DATABASE, so a locomotive can be deleted while the tile's orphaned object is mid-route driving it; the orphan iterates a snapshot (CS3-B1) and logs "locomotive does not exist" for the rest, so this costs nothing new - it is noted because the door's guarantee is narrower than its comment says.

**Why B and not A.**  The commands sent are a route the operator once wrote, not garbage, and every door with a person at it still asks the conflict question of the (old) route's accessories first.  It needs an edit to a route that is drawn as a tile, and it heals on the next session or the next diagram edit.  Against that: it needs no coincidence and no second thread, and with the Central Station as the source there is no operator action short of Switch to CS Layout that clears it.  If Adam edits station routes and then drives from the tiles, this is an A on his railway and should be relettered - the identifier stays.

**How to prove it.**  In the shape of `core.testRoutes`, `model = init(null, true, false, false, true)`, no fixture needed - a page can be built in code:

1. `List<RouteCommand> before = [RouteCommandAccessory(90, MM2, true), RouteCommandAccessory(91, MM2, true)]`; `model.newRoute("Tile", 21, before, 0, CLEAR_THEN_OCCUPIED, false, null)` (the by-id door, `:2173`).
2. `LayoutDiagram page = new LayoutDiagram("P", 4, 4, "", model); page.addComponent(componentType.ROUTE, 1, 1, 0, 0, 21, 21, null, null)` (signature at `LayoutDiagram:119`; `parseLayout` builds route tiles with `address` = the route id, `:2641-2665`); `model.wireComponents(page, null)`; `LayoutDiagramComponent tile = page.getComponent(1, 1)`.  **Assert the precondition**: `tile.getRoute() == model.getRoute(21)` - green today, and the test proves nothing without it.
3. `List<RouteCommand> after = [RouteCommandAccessory(95, MM2, true)]`; `model.editRoute("Tile", "Tile", after, 0, CLEAR_THEN_OCCUPIED, false, null)`.  **Assert `tile.getRoute() == model.getRoute(21)`** - red: the tile holds the object `deleteRoute` removed.
4. `model.setSentMessageObserver(m -> if (m.isAccessoryCommand()) sent.add(m.extractUID()))`; `tile.execSwitching()`; wait, bounded at 3 s, for `((MarklinRoute) tile.getRoute()).isExecuting()` to go false.  **Assert `sent` contains UID(95) and not UID(90)** - red: 90 and 91 went out.
5. The delete door: `model.deleteRoute("Tile")`; clear `sent`; `tile.execSwitching()`; wait as above.  **Assert `sent` is empty** - red: the deleted route's two commands go out.
6. The sync door, without a station: `model.deleteRoute(...)` then `model.newRoute(new MarklinRoute(model, "Tile", 21, after, 0, CLEAR_THEN_OCCUPIED, false, null))` is the exact pair `syncWithCS2` runs at `:1478` and `:1484`; the same asserts go red.

**The fix, and what it has to decide.**  The smallest change is at the point of use: `execSwitching` (`LayoutDiagramComponent:181-183`) and the two `LayoutLabel` readers resolve the route THROUGH the model by id at click time (`network.getRoute(this.address)`), and treat null as "no such route" with a log line - which is what `wireComponents` already says at wiring time (`:762`).  That makes the stored object a cache rather than the truth, and a deleted route's tile does nothing.  The highlight (`LayoutGrid:1867-1869`) is the other half and belongs to the GUI reviewer: either register labels on the new object when a route is re-added (a `MarklinRoute` constructor argument, or a `tiles` hand-over in `editRoute`), or have `updateTiles` look the labels up by route id.  Alternatively `editRoute` could mutate the existing object instead of swapping it - but `MarklinRoute.route` is the list CS3-B1 just made snapshot-on-read, and the route page's table holds live objects too (the VLD-C3 note at `TrainControlUI:19366`), so that is the larger change.  Whichever is chosen, grep the four doors above before closing: `editRoute`, the sync's two deletes, `importRoutes` and `deleteRoute`.

### MKR-C1 - the parser swap RC-B9 guarded against still reaches the two counts the guard was written for

`syncWithCS2` assigns `this.fileParser = new CS2File(cs2Address(), this)` at `:1393`, outside `layoutRefreshLock`, which it takes at `:544` only when it reaches `syncLayoutsFromConfiguredSource`.  `syncLayouts` runs under that lock and reads the field four times: `getMagList` (`:781`), `parseLayout` (`:796`), `getPagesThatCouldNotBeRead` (`:805`) and `getPagesTheIndexNamed` (`:815`).  The comment at `:798-804` records the hazard - "a concurrent refresh could have put a fresh parser there, the second question would have been answered with its zero" - and says "a local removes the question rather than answering it".  It does not: the local is assigned from a SECOND read of the field, after `parseLayout` has returned.  `parseLayout` resets both counters to zero on entry (`CS2File:2465`, `:2467`) and a fresh `CS2File` starts with both at zero (`:2428`, `:2431`), so a refresh whose parse straddles the swap reads `0` and `0` from a parser that parsed nothing.

**Reachability.**  A refresh has to be inside `parseLayout` when a sync starts.  Refreshes run on their own thread from `layoutEditingComplete` (`TrainControlUI:23189-23199`, after a diagram edit or a route editor Save); syncs run on a worker or a background thread from a dozen doors, and the UI's `syncInFlight` guard (`TrainControlUI:11661`) serialises sync against sync, not sync against refresh.  The sync then blocks at `:544` until the refresh finishes, so the two never run `syncLayouts` together - only the swap lands inside the refresh's parse.  The window is the parse of a local folder, tens of milliseconds for five pages, and it costs something only when a page failed to read in that parse: `couldNotBeRead` reads 0, so the prune at `:887-902` runs on a partial railway (the RC-A3 case), or `actuallyRead == 0` with both counts 0 skips the throw at `:856` and `clearLayouts()` empties the diagram (the RC-A4 case).  A trap with a comment claiming it is closed, which is the shape the SOP says to write down.

**How to prove it.**  Reading is enough here - the field is read at `:796` and again at `:805` - but a test can force it: inject a `CS2File` subclass whose `parseLayout` blocks on a latch, call `refreshLayouts()` on a thread, release nothing, call `syncWithCS2()` on a second thread (it swaps the field and blocks on the lock), release the latch, and assert the log carries `layout.pruningSkippedPageUnreadable` for a fixture with one unreadable page - red today.  **Fix**: `final CS2File parser = this.fileParser;` at the top of `syncLayouts` and every read through it - which is what the comment already describes.

### MKR-C2 - the other half of CS3-C3: a re-addressed locomotive's echoes are dropped without even the "unknown locomotive" line

CS3-C3 found that the five-argument `newLocomotive` did not rebuild `locIdCache`, and it was fixed there (`:3047-3051`).  The same loop has a second door that changes a UID: the address update at `:1563-1568` calls `setAddress` (which recomputes the UID, `MarklinLocomotive:443`), deletes and re-adds the locomotive under its new `getUID()` key, and rebuilds nothing.  The cache is rebuilt once, at `:1634`, on the success path only; the `finally` CS3-C3 suggested was not adopted.  Between `:1568` and `:1634` - the rest of the locomotive loop, milliseconds normally - and for good if anything later in the loop throws, `receiveMessage`'s locomotive branch resolves the new UID to `locIdCache.get(id) == null` (`:2575`) and takes NO branch: the `logf("network.unknownLocomotiveCommand")` at `:2607` is inside `if (locs != null)`, so a UID the cache has never seen is dropped in silence, unlike a UID it has seen with no locomotive left on it.  The old UID's entry still names the locomotive, and `locDB.getById("name_oldUID")` returns null (`:2585-2595`), so those are dropped too.  `changeLocAddress` (`:3189`) rebuilds; only the sync's door does not.  A locomotive that changed address on the station and is then driven from the station shows a stale speed in TrainControl until the next add, rename, delete or successful sync - and nothing in the log says why.

**How to prove it.**  A sync cannot be driven without a station, but the two statements can: `model.newMM2Locomotive("Moved", 5)`; deliver a velocity echo for MM2 UID 5 and assert the speed lands (precondition); then run the pair at `:1563-1568` through a test hook - or, absent one, assert by reading that `rebuildLocIdCache()` is called between `:1568` and `:1634`.  **Fix**: rebuild after `:1568`, or move `:1634` into a `finally` as CS3-C3 proposed, and make the `locs == null` branch log the same line the empty-list branch does.

### MKR-C3 - Backup Data serialises the live command list the CS3-B1 fix left editable in place

`dad874e6` made every walk of `MarklinRoute.route` on the route thread iterate a copy (`hasEmergencyStop:418`, `accessoryHeldByAutonomy:440`, `execRoute:700`, `setDelay:1141`), and `deleteLoc` still removes from the live list through `Route.locomotiveDeleted` (`:194-198`, `Iterator.remove()`).  The walkers that were not swept - `otherRouteRenamed`, `locomotiveRenamed`, `commandsDrive`, `toCSV`, `toJSON` - all run on the event thread with `deleteLoc`, so they are safe by exclusion.  One does not: `saveState` (`:1719-1722`) builds `new MarklinSimpleComponent(r)`, whose constructor stores `this.route = r.getRoute()` (`MarklinSimpleComponent:90`) - the list itself, not a copy - and `writeAtomically` then serialises it (`:1777-1784`).  Backup Data runs `model.saveState(false)` on a thread of its own (`TrainControlUI:21942`, `:21982`).  A locomotive delete on the event thread while that thread is inside `ObjectOutputStream.writeObject` throws `ConcurrentModificationException` from `ArrayList.writeObject` (or corrupts the walk of a `LinkedList`, which has no modCount check in its writer and simply writes whatever nodes it reaches).  `writeAtomically` catches `RuntimeException` and deletes the staging file (`Util:531-538`), so `LocDB.data` is untouched - but `saveState` catches only `IOException` (`:1788`), so the exception leaves the model and the backup thread's try at `TrainControlUI:21965` decides what the operator sees.  The window is the serialisation of the route list, single-digit milliseconds on Adam's database; a delete has to land in it.  Written up because the fix's own comment promises "every walk of this command list takes a copy first" and this walk is off the event thread.

**How to prove it.**  Not the race - the invariant: `assertNotSame(new MarklinSimpleComponent(route).getRoute(), route.getRoute())` is red today and is the property a fix would establish.  **Fix**: copy in the constructor, `this.route = new ArrayList<>(r.getRoute())`, which is one line and also stops a later edit from changing a snapshot already taken.

### MKR-C4 - `getRouteList` can throw on a route the sync is replacing at that instant

`getRouteList` (`:3646-3658`) takes `routeDB.getItemIds()` - a copy, under the collection's lock - sorts it, and then calls `this.routeDB.getById(i).getName()` for each id outside any lock.  The sync's re-read (`:1478` then `:1484`) removes an id and puts it back a few statements later, on a background thread; `getRouteList` is called from the event thread by `runningRouteDriving` (`:3275`, today's CS3-B1 door), by `refreshRouteList` (`TrainControlUI:29543`) and by six other readers, and from `BulkEnableOrDisable`'s own thread (`:21380`).  The route-deletion window is microseconds and the reader has to land in it, so this is a trap rather than a fault anybody has seen - but `receiveMessage` was given exactly this treatment twice (`:2516-2520`, `:2618-2622`: "resolved once into a local ... the resulting NPE would be swallowed"), and here the NPE is not swallowed; on the event thread it is a stack trace out of a menu action.  Twins checked: `getLayoutList` (`:3804`) and `getLocList` (`:3142`) return names only; the prune at `:893-899` does the same id-then-lookup on `feedbackDB` but under the lock nothing else deletes from.  **Fix**: null-check the lookup, or build the list from `getItems()` sorted by id.

**MKR-D1.**  This looked like S14-A1 again: `newRoute(MarklinRoute)` disarms the routes it refuses (`:2138`, `:2155`) with a comment about a monitor started "as soon as the route is enabled and has an s88 - before the object has been offered to any database", and the sync's loop does not call `newRoute` at all for a route it already holds unchanged (`:1481`), so a parsed route with a live monitor would have been left running for the session, one more per sync.
