# The last day, reviewed — 2026-08-25

Four independent reviewers over `48d98f4c..HEAD`: 118 commits, 20,543 insertions across 83 source and
test files, split by area — the autonomy model, the setup store and session, the interface, and the
test suite with its harness. Adam asked for it after the round closed.

Prefix `LD`. Every other two-letter prefix in this folder is taken.

## What it found, in one sentence

**Nine defects, and seven of them were in the work of that same day.** The reviewers were asked to
look for regressions and omissions, and that is overwhelmingly what was there: not old code decaying,
but new guards that were wrong in a direction nobody had checked. Two of them would have destroyed
work the operator had explicitly saved.

The most useful thing in the whole exercise is not any single finding. It is that **the round which
produced these defects also produced a document saying it had validated them.** Four review passes and
two validation passes ran that day. They found real things. They did not find these, and the reason
they did not is worth more than the fixes: every one of these nine was found by *running* something —
a probe, a mutation, a fixture — and the passes that missed them were reading.

## The findings

### LD-1 — the autonomy editor began an edit session it never ended

**Found by:** the interface review and the store review, independently. The store review reproduced it
on a scratch copy of Adam's real configuration. **Fixed:** `0665608e`.

OB-108 writes a snapshot of the setup to disk when the layout editor opens, so that a process that
dies mid-edit can be undone. `beginEditSession` is called from the constructor, which serves both of
the editor's modes. All three `endEditSession` calls sat on the track-editor side of an
`if (isAutonomyMode())`.

So every autonomy *setup* editing session left its note behind, and the next session build found it
and reverted the setup to how it stood before that editor opened.

**Spend an evening naming stations, setting lengths, pairing signals and placing locomotives. Press
Save. Restart the next day and the evening is gone**, with one line in the log about an edit that did
not finish.

That is worse than the defect OB-108 was fixing. OB-108 protects unsaved work against a crash; this
destroyed *saved* work on an ordinary exit. The commit that introduced it names this exact failure —
"a note left behind by a clean Save would throw away the edit the user just made… It is a test, not a
comment" — and the test drives `AutonomySession` directly, so it could not see the wiring.

The fix is not a fourth `endEditSession` call. The note now mirrors `autonomyAsOpened` exactly, which
is the invariant it always had: one method takes both halves so they cannot be taken at different
moments, and `dispose()` gives it back — the one thing all seven ways of closing that window pass
through. A page or mode switch keeps the frame and re-takes the note, which matters: the first version
took it in the constructor only, so a switch moved the memory half and left the disk half describing
the window's opening, which would have reverted work the operator was asked about and chose to save on
the way there.

### LD-2 — the route guard refused a signal for being set to the aspect protection itself wants

**Found by:** the autonomy review, which ran it. **Fixed:** `0665608e`.

The guard has two halves and they are not the same rule. A turnout on a locked path must not move at
all — any position but the one the path configured is wrong for the train crossing it. A protecting
signal is different: **the only harmful command is the one that turns protection off.**

The first version asked neither question. It refused any route touching any protecting signal of any
platform with a train standing at it, whether or not a path was locked anywhere, and whichever aspect
the route was asking for. Because accessories are skipped as a group, one such signal took every
turnout in that route with it.

Review reproduced it with nothing locked anywhere: `getActiveAccs` empty, `conflictingAccessory`
non-null, the whole route's ironwork silently unmoved. On a railway with 39 s88-triggered routes and
trains parked at platforms — which is all the time — that is most of the layout's routes not working.

This is precisely the over-strictness Adam predicted when he said he would rather have no check than
one that is too tight. The log also blamed "a train running over it" for a train that was parked.

### LD-3 — a refused hand dispatch commanded every protecting signal on the layout

**Found by:** the autonomy review, which ran it with a speed of zero. **Fixed:** `0665608e`.

The signal sweep added for hand dispatches ran at the top of `executePath`, before all eight checks
that can turn a dispatch away. Ask for a bad one — speed out of range, empty path, train not at the
start, already running — and the signals were commanded on the way to being told no.

And they stayed. The thread count falls straight back to zero, `isRunning()` goes false, and the
per-occupancy refresh is deliberately silent while nothing runs, so nothing would correct them until
something else started a run.

Right-click, dispatch, get "invalid speed", and the platform signals across the layout change aspect
anyway and stay there. The rule being broken is one the same file states for itself a few hundred
lines further down: the railway is not commanded while the operator is still deciding what it should
look like. A refusal is that moment.

### LD-4 — the pre-edit note was applied without being checked

**Found by:** the store review, which fed it four sidecars. **Fixed:** `5d4d3dd0`.

`restoreSetup` was written for what `snapshotSetup` produces: it clears the store and then reads. That
is safe for an object of known shape and unsafe the moment the contract moves to a *file* — written by
another run, possibly by another build. Only "not JSON at all" was handled.

| note | what happened |
|---|---|
| `{}` | threw out of `getJSONObject("shared")` **after** the clear — autonomy dead for the rest of the session, and the note still there to do it again at the next start |
| `{"shared":{"version":99},…}` | accepted, where `load()` refuses exactly that because "silently dropping fields it does not recognise would lose the user's work on the next save" |
| not JSON | correctly ignored |

`unfinishedEdit` now makes the same checks `load()` makes. It refuses what it cannot use and **keeps**
it: a version 99 note belongs to the newer TrainControl that wrote it and will be run next, and
deleting it on the way past would throw away that build's safety net. What must not happen is silence,
so the session can tell "no note" from "a note that was refused", and the interface says the second
out loud.

The fourth case review offered — well formed but empty — turned out **not to be refusable**. A note is
a snapshot taken when the editor opened, so an empty one is exactly what a setup that was empty at
that moment produces, and reverting to empty is then correct. Nothing in the file distinguishes that
from corruption, and refusing it would break the case the mechanism exists for. Written into the test
rather than argued about again.

Two more from the same review, in the same commit. `deleteEverything` left the note, so the way back
out of having set autonomy up at all restored the whole deleted setup on the next start — confirm a
two-step deletion, watch it happen, get it all back. And `forgetBeforeEdit` dropped the result of
`delete()`: this setup lives under OneDrive, `save()` goes through `writeAtomically` because the
folder can be locked by a sync client, and this was the one file operation here whose result nobody
looked at. It now reports, and a note that cannot be removed is overwritten with the setup as it
stands — a note that reverts to the present changes nothing.

### LD-5 — the suite reported things it had not checked

**Found by:** the test and harness review. Every item confirmed by running it. **Fixed:** `7bd0e10a`.

- **A test whose named mutation did not fail it.**
  `testAnUnchangedLayoutSerialisesTheSameWayTwice` built two sets "in opposite orders" out of
  `HashSet`s, which discard order — with three elements in a sixteen-slot table both iterate
  identically, so it compared two strings that were equal whatever `toJSON` did. Review ran the
  mutation the javadoc names **eight times and got eight passes**; one word later it failed. The
  property it guards is the one that stopped the window quietly rewriting Adam's own railway on every
  launch.
- **A mutation claim that was simply false.** The rename matrix said its third column catches
  `toStored` returning its argument. It does not — review neutered `toStored` and the failure came
  from a different column. The same file says so correctly sixty lines later; the two were written the
  same day. Trimming the matrix on the strength of the wrong one would have deleted the only column
  that can catch a raw page name in `setup.json`.
- **Two fixture guards that could not fire**, in the file that documents that exact trap forty lines
  away and had fixed the assertion it was written for without carrying it back.
- **The battery counted a class that ran zero tests as green.** `Total tests run: 0, Failures: 0,
  Skips: 0` satisfies both existing branches, so two support classes holding no tests have been in the
  green count on every run — it was inflated by two.
- **And it never read the second summary line.** TestNG prints `Configuration Failures:` separately,
  so a class whose `@AfterClass` throws read as green. The teardowns here are load-bearing: one of
  them puts two of Adam's real signals back to green and says why.
- **`reap.ps1` killed another run's JVMs.** The match was a prefix and `RUN_ID` is `battery-$$`, so
  `battery-777` matched `battery-7777`. The file claimed two batteries could run at once "proven
  rather than assumed"; the proof used three ids, none a prefix of another.

The battery's own header names the shape it keeps repeating — *the runner decided what a run meant by
looking at part of it* — and these were the third and fourth instances of it in two days.

### LD-6 — cancelling the crop dialog replaced the icon and deleted the old one

**Found by:** the interface review. **Fixed:** `b75876fa`.

`cropLocIcon` returned null for "the user pressed Cancel" and for "the picture could not be read", and
the caller fell back to the uncropped file for both. So picking a photo, ticking Crop, and then
pressing Cancel set the full photograph as the locomotive's icon **and deleted the crop that was there
before**. Escape and the close box landed in the same place.

The crop dialog's own javadoc already said null meant "leave everything exactly as it was, **not** a
failure". The two contracts were written the same day and the running code followed the wrong one.

### LD-7 — the route tile threw away the answer to "turn the power on first?"

**Found by:** the interface review. **Fixed:** `b75876fa`.

The route-conflict block was inserted between the power-off dialog that sets `powerOnFirst` and the
worker that consumes it, and it returned. So agreeing to "turn power on and proceed" ran the route
into a dead track with the power still off, silently.

That is exactly the case the override exists for: recovering a turnout that did not take its command,
after an emergency stop. It now runs on the worker after the power, like everything else that tile
does — which is also a better moment to ask, since the answer is less likely to have gone stale.

### LD-8 — Adam's home ruling reached one door of three

**Found by:** the autonomy review, which proved both bypasses with a probe. **Fixed:** `b75876fa`.

The rule — a square drawn as more than one graph Point cannot be a home — was put at
`setHomeLocomotive`, with a comment claiming that was "the one door everything comes through". Review
walked the other two.

- `parseAuto` calls `Point.setHomeLoc` directly, so a hand-edited or imported configuration installed
  the forbidden home unchallenged. **That is the case the model door was added for**, since a file
  cannot be greyed out.
- The positional default in `claimHome` makes a square the home of whatever is standing on it, with no
  check at all — and that is the state every layout with no explicit assignments is in, **including
  Adam's own**.

So the state he ruled invalid remained the *default* wherever a train was parked on such a square. The
rule was missing exactly where it mattered most.

Each door now gets the treatment it can take: the file says so and skips the one line, because one bad
home is not a reason to refuse a railway; the positional default simply does not notice such a square,
because nobody asked for that home.

### LD-9 — the menu offered a home the model then refuses

**Found by:** the autonomy review. **Fixed:** `b75876fa`.

`canBeHome` is false for two unrelated reasons and both callers read it as one. On a multi-Point
square the right-click menu showed "no train can come to rest here" — a different claim, and not the
true one — and that dialog is deliberately warn-and-proceed, so answering Yes went on to
`setHomeLocomotive`, which throws for that case, and put up a second dialog contradicting the first.

`whyNotAHome` was split out for precisely this and had no caller but `canBeHome`, so the stated
purpose was unrealised. It has two now, and each acts on the answer it is about.

This is the guard-and-affordance rule again, which is now the most-repeated finding in this
repository: **the control that offers an action must ask the guard's own predicate.**

## Filed, not fixed

- **`getActiveAccs` and `conflictingAccessory` read `Layout.points`, a plain `HashMap`, off-thread.**
  A pre-existing hazard that `getPoints`' own javadoc already records as "real and unaddressed… filed
  rather than done in a hurry"; the route guard added a second caller class to it. Reported as a
  suspicion — no `ConcurrentModificationException` was produced.
- **`Edge.isLockHeld`'s comment describes a mechanism the code does not use.** It says "a route locks
  the edges it crosses AND checks the edges that lock it"; both operations use the same list in the
  same direction. The *conclusion* is still true — the reviewer traced both orderings of an asymmetric
  relation and each is refused — so this is a wording defect in a comment the repository treats as
  load-bearing, not a locking bug.
- **`captionIsActive` may hide every station name** in the window between `resetAutonomySession`
  nulling the field and something rebuilding it, because the guard asks `model.hasAutoLayout()` and
  the data comes from the session field. Suspicion: the reviewer did not establish that a grid rebuild
  lands inside that window. The asymmetry is real either way and the fallback points the unsafe way.
- **The station right-click menu walks the whole graph four times on the EDT**, purely to decide one
  enabled flag and one tooltip. Correct, and asking the right predicate — just asking it four times.
- **`testTheGoldenLayoutHoldsTogether`'s javadoc claims a scope it does not have.** It says it would
  have caught another class writing to the live layout; both its captures are in the same JVM, so it
  can only see its own writes. Not vacuous — mis-scoped. The protection against that folder lives in
  `battery.sh`, which is what actually has it.
- **`HELD_FIELDS` is a thirteenth bookkeeping site** that the new registry does not cover and the
  textual guard does not check. A new collection added to `kept()` and omitted there would lose that
  page's entries on any save made while a page file is missing.
- **`testConfirmedGoodState` has never tested anything** — `test/baseline` was never captured or
  committed, so both its methods skip. Known; it is the one class the battery reports as having tested
  nothing, and it is waiting on MT-140.

## What this says about how the round went

The round that produced these nine defects ran four review passes and two validation passes, and
closed with a document describing what they had caught. They caught real things. They did not catch
any of these.

The pattern is not subtle. **Seven of the nine are guards written the previous day, and every one of
them was found by running something.** LD-2 needed a probe with nothing locked. LD-3 needed a dispatch
with a speed of zero. LD-5's first item needed the mutation its own javadoc named, run eight times.
LD-8 needed a fixture with a home in the file rather than in a method call. The passes that missed
them were reading code and reasoning about it — which is exactly what produced the defects in the
first place, so it is not surprising that it did not find them.

Three narrower lessons, each of which cost something here:

**A new guard has two failure directions and reviewing one is not reviewing it.** Every guard added
that day was checked for "does it refuse the dangerous case". None was checked for "what does it
refuse that it should not", which is where LD-2, LD-3 and LD-9 all live. Adam had to say this out loud
— "be careful with auto disallowed routes to avoid regression" — before it was looked at, and he was
right both times he said it.

**A rule placed at "the one door everything comes through" needs that phrase checked, not written.**
LD-8's comment asserted it. Two other doors were a grep away. The same shape produced LD-1: three
endings wired, four not, in a method whose modes are visible in the same file.

**A test that has not been run against its own claimed mutation is a comment.** LD-5's first item had
carried a `MUTATION:` line for a day, and the line was false. That is the fourth vacuous test found in
two days, and the only reliable way any of them was found was by someone applying the mutation and
watching.
