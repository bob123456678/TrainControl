### LD-A1 — the autonomy editor began an edit session it never ended

`LayoutEditor.java`, constructor against the three endings.

**Found by:** the interface review and the store review, independently. The store review reproduced it
with a probe on a scratch copy of Adam's real configuration.

OB-108 writes a snapshot of the setup to disk when the layout editor opens, so a process that dies
mid-edit can be undone. `beginEditSession` is called from the constructor, which serves both of the
editor's modes. All three `endEditSession` calls sat on the track-editor side of an
`if (isAutonomyMode())`.

So every autonomy *setup* editing session left its note behind, and the next session build found it and
reverted the setup to how it stood before that editor opened.

**What the operator sees.** Spend an evening naming stations, setting lengths, pairing signals and
placing locomotives. Press Save. Restart the next day and the evening is gone, with one line in the log
about an edit that did not finish.

That is worse than the defect OB-108 was fixing. OB-108 protects unsaved work against a crash; this
destroyed *saved* work on an ordinary exit. The commit that introduced it names this exact failure —
"a note left behind by a clean Save would throw away the edit the user just made… It is a test, not a
comment" — and the test drives `AutonomySession` directly, so it could not see the wiring.

The fix is not a fourth `endEditSession` call. The note now mirrors `autonomyAsOpened` exactly, which
is the invariant it always had: one method takes both halves so they cannot be taken at different
moments, and `dispose()` gives it back — the one thing all seven ways of closing that window pass
through. A page or mode switch keeps the frame and re-takes the note, which matters: the first version
took it in the constructor only, so a switch moved the memory half and left the disk half describing
the window's opening, which would have reverted work the operator was asked about and chose to save on
the way there.

### LD-A2 — the pre-edit note was applied without being checked

`AutonomyCompanionStore.unfinishedEdit`, applied through `restoreSetup`.

**Found by:** the store review, which fed it four sidecars and watched what each did.

`restoreSetup` was written for what `snapshotSetup` produces: it clears the store and then reads. That
is safe for an object of known shape and unsafe the moment the contract moves to a *file* — written by
another run, possibly by another build. Only "not JSON at all" was handled.

| note | what happened |
|---|---|
| `{}` | threw out of `getJSONObject("shared")` **after** the clear — autonomy dead for the rest of the session, and the note still there to do it again at the next start |
| `{"shared":{"version":99},…}` | accepted, where `load()` refuses exactly that because "silently dropping fields it does not recognise would lose the user's work on the next save" |
| not JSON | correctly ignored |

`unfinishedEdit` now makes the same checks `load()` makes. It refuses what it cannot use and **keeps**
it: a version 99 note belongs to the newer TrainControl that wrote it and will be run next, and
deleting it on the way past would throw away that build's safety net. What must not happen is silence,
so the session can tell "no note" from "a note that was refused", and the interface says the second out
loud.

Two more from the same review, in the same commit. `deleteEverything` left the note, so the way back
out of having set autonomy up at all restored the whole deleted setup on the next start — confirm a
two-step deletion, watch it happen, get it all back. And `forgetBeforeEdit` dropped the result of
`delete()`: this setup lives under OneDrive, `save()` goes through `writeAtomically` because the folder
can be locked by a sync client, and this was the one file operation here whose result nobody looked at.
It now reports, and a note that cannot be removed is overwritten with the setup as it stands — a note
that reverts to the present changes nothing.

The fourth sidecar the reviewer offered is withdrawn as **LD-D1**.

**The fallback described above was itself defective** - see
[FB-A2](2026-08-25-independent-fable.md). It overwrote the note through `writeAtomically`, which ends
in a `Files.move(REPLACE_EXISTING)` that needs the very DELETE access the failed `delete()` lacked, so
it failed in exactly the case it was written for and left the pre-edit snapshot in place. Fixed in
`0e1d2c14` by writing in place.

### LD-A3 — the route guard refused a signal for being set to the aspect protection wants

`MarklinRoute.accessoryHeldByAutonomy`.

**Found by:** the autonomy review, which ran it.

The guard has two halves and they are not the same rule. A turnout on a locked path must not move at
all — any position but the one the path configured is wrong for the train crossing it. A protecting
signal is different: **the only harmful command is the one that turns protection off.**

The first version asked neither question. It refused any route touching any protecting signal of any
platform with a train standing at it, whether or not a path was locked anywhere, and whichever aspect
the route was asking for. Because accessories are skipped as a group, one such signal took every
turnout in that route with it.

Review reproduced it with nothing locked anywhere: `getActiveAccs` empty, `conflictingAccessory`
non-null, the whole route's ironwork silently unmoved.

**What the operator sees.** On a railway with 39 s88-triggered routes and trains parked at platforms —
which is all the time — most of the layout's routes quietly stop working while autonomy runs. The log
blamed "a train running over it" for a train that was standing still.

This is precisely the over-strictness Adam predicted when he said he would rather have no check than
one that is too tight.

### LD-A4 — a refused hand dispatch commanded every protecting signal on the layout

`Layout.executePath`.

**Found by:** the autonomy review, which ran it with a speed of zero.

The signal sweep added for hand dispatches ran at the top of `executePath`, before all eight checks
that can turn a dispatch away. Ask for a bad one — speed out of range, empty path, train not at the
start, already running — and the signals were commanded on the way to being told no.

And they stayed. The thread count falls straight back to zero, `isRunning()` goes false, and the
per-occupancy refresh is deliberately silent while nothing runs, so nothing would correct them until
something else started a run.

**What the operator sees.** Right-click, dispatch, get "invalid speed", and the platform signals across
the layout change aspect anyway and stay there.

The rule being broken is one the same file states for itself a few hundred lines further down: the
railway is not commanded while the operator is still deciding what it should look like. A refusal is
that moment.

### LD-A5 — Adam's home ruling reached one door of three

`Layout.setHomeLocomotive`, against `parseAuto` and `claimHome`.

**Found by:** the autonomy review, which proved both bypasses with a probe.

The rule — a square drawn as more than one graph Point cannot be a home — was put at
`setHomeLocomotive`, with a comment claiming that was "the one door everything comes through". Review
walked the other two.

- `parseAuto` calls `Point.setHomeLoc` directly, so a hand-edited or imported configuration installed
  the forbidden home unchallenged. **That is the case the model door was added for**, since a file
  cannot be greyed out.
- The positional default in `claimHome` makes a square the home of whatever is standing on it, with no
  check at all — and that is the state every layout with no explicit assignments is in, **including
  Adam's own**.

So the state he ruled invalid remained the *default* wherever a train was parked on such a square. The
rule was missing exactly where it mattered most.

Each door now gets the treatment it can take: the file says so and skips the one line, because one bad
home is not a reason to refuse a railway; the positional default simply does not notice such a square,
because nobody asked for that home.

### LD-A6 — cancelling the crop dialog replaced the icon and deleted the old one

`TrainControlUI.cropLocIcon` and its caller.

**Found by:** the interface review.

`cropLocIcon` returned null for "the user pressed Cancel" and for "the picture could not be read", and
the caller fell back to the uncropped file for both. So picking a photo, ticking Crop, and then
pressing Cancel set the full photograph as the locomotive's icon **and deleted the crop that was there
before**. Escape and the close box landed in the same place.

The crop dialog's own javadoc already said null meant "leave everything exactly as it was, **not** a
failure". The two contracts were written the same day and the running code followed the wrong one.

The least severe of the A items — the loss is one icon file and is recoverable by cropping again — but
it is silent and it is destruction of something the operator made, so it sits here rather than in B.

### LD-B1 — the route tile threw away the answer to "turn the power on first?"

`LayoutLabel.java`, the route-conflict block.

**Found by:** the interface review.

The block was inserted between the power-off dialog that sets `powerOnFirst` and the worker that
consumes it, and it returned. So agreeing to "turn power on and proceed" ran the route into a dead
track with the power still off, silently.

That is exactly the case the override exists for: recovering a turnout that did not take its command,
after an emergency stop. It now runs on the worker after the power, like everything else that tile does
— which is also a better moment to ask, since the answer is less likely to have gone stale.

### LD-B2 — the home menu offered a home the model then refuses

`HomeLocomotiveMenu.java`, and `AutonomyEditorPanel.mayRestHere`.

**Found by:** the autonomy review.

`canBeHome` is false for two unrelated reasons and both callers read it as one. On a multi-Point square
the right-click menu showed "no train can come to rest here" — a different claim, and not the true one
— and that dialog is deliberately warn-and-proceed, so answering Yes went on to `setHomeLocomotive`,
which throws for that case, and put up a second dialog contradicting the first.

`whyNotAHome` was split out for precisely this and had no caller but `canBeHome`, so the stated purpose
was unrealised. It has two now, and each acts on the answer it is about.

This is the guard-and-affordance rule again, which is now the most-repeated finding in this repository:
**the control that offers an action must ask the guard's own predicate.**

### LD-B3 — a test whose named mutation did not fail it

`testHomeStaging.testAnUnchangedLayoutSerialisesTheSameWayTwice`.

**Found by:** the test review, which ran the mutation eight times.

The test built two sets "in opposite orders" out of `HashSet`s, which discard order — with three
elements in a sixteen-slot table both iterate identically, so it compared two strings that were equal
whatever `toJSON` did. Removing the `Collections.sort` the javadoc names gave **eight passes out of
eight**; changing one word to `LinkedHashSet` made it fail.

The property it guards is the one that stopped the window quietly rewriting Adam's own railway on every
launch.

### LD-B4 — the battery counted a class that ran zero tests as green, and never read the second summary line

`tools/battery.sh`.

**Found by:** the test review, which reproduced both.

`Total tests run: 0, Failures: 0, Skips: 0` satisfies both existing branches, so two support classes
holding no tests have been in the green count on every run — it was inflated by two. The same shape
catches a class that has lost its `@Test` annotations.

And TestNG prints `Configuration Failures:` on a *separate* line, which the runner never read, so a
class whose `@AfterClass` throws read as green. The teardowns here are load-bearing: one of them puts
two of Adam's real signals back to green and says why.

The battery's own header names the shape it keeps repeating — *the runner decided what a run meant by
looking at part of it* — and these were the third and fourth instances of it in two days.

### LD-B5 — `reap.ps1` killed another run's JVMs

`tools/reap.ps1`.

**Found by:** the test review, which reproduced it with three marked JVMs.

The match was a prefix and `RUN_ID` is `battery-$$`, so `battery-777` matched `battery-7777`. The file
claimed two batteries could run at once "proven rather than assumed"; the proof used three ids, none a
prefix of another. The victim dies at exit 127 with no output and reads as a hanging test.

Verified in both directions after the fix: with 777, 7777 and 888 alive, reaping 777 kills exactly one,
and the other two are still reapable by their own ids.

### LD-B6 — a conflict that cleared between check and dialog dropped the route silently

`TrainControlUI.confirmRouteOverActivePath`.

**Found by:** the interface review. Control-flow claim confirmed by reading; the race itself was not
reproduced, and the reviewer said so.

The method returned false for "there is nothing to confirm" and for "the user said no", and both
callers treat false as "do not run it". Autonomy releases accessories from its own threads as trains
move, so the conflict really can clear between the caller's check and this one — and when it did, the
route did nothing at all, with no dialog and no log line, because the model's own refusal was never
reached either.

The question the method answers is "may this route run", and with no conflict the answer is plainly
yes.

### LD-B7 — `heldFields` is a thirteenth bookkeeping site the registry does not cover

`AutonomyCompanionStore`, against `testStoreCollectionsAreHandledEverywhere`.

**Found by:** the store review. A claim about a future addition rather than a live defect, and the
reviewer said so.

`heldFields` says how each collection's entries are picked out of the file when their page is not
loaded, and held back verbatim. It cannot be derived from the OB-025 registry — it is about the shape
entries have in the *file* rather than about the collection, and it is static, so `kept()` is not
available to it.

Before the registry it was shadowed by accident: `sharedFields` carried a literal list of the same
twelve names that the textual guard read, so a collection missing from `heldFields` was usually missing
from that list too. `sharedFields` is a loop now and the shadow went with it.

It is a method rather than a static block so the guard can address it by name, and it is in `SITES`.
The cost of an omission is in its own javadoc: one save while a page's file is missing deletes that
page's entries for the collection nobody listed.

The reviewer did not establish that a rebuild actually lands in that window and labelled it a

points the unsafe way. **Open.**

### LD-D1 — a well-formed but empty pre-edit note *(withdrawn, originally A)*

The store review offered `{"shared":{},"configurations":{}}` as a fourth bad sidecar under A2, on the
grounds that it empties the setup and saves it.

**It is not refusable.** A note is a snapshot taken when the editor opened, so an empty one is exactly
what a setup that was empty at that moment produces — and reverting to empty is then *correct*, which
is the whole point when the operator built the setup during the edit and the process died. Nothing in
the file distinguishes that from corruption, and refusing it would break the case the mechanism exists
for.

Written into the test as a comment rather than argued about again.

### LD-D2 — the revert guard reading `openEditor` before it is assigned *(withdrawn)*

The interface review noted that `openEditor` is only assigned after `new LayoutEditor(...)` returns,
while the constructor calls `getAutonomySession()` — so the `editorOpen` guard added for OB-108 reads a
stale value during construction.

True, and benign. A disposed editor answers `isDisplayable()` false, which is the correct answer, and
on a first open the field is null, which is also correct. The reviewer flagged it as an *amplifier* of
A1 rather than a defect in itself, and with A1 fixed there is no leaked note for it to act on. The case
the guard was actually added for — a session rebuilt while an editor is open — goes through a different
call, where `openEditor` is properly assigned.

### LD-D3 — the OB-025 registry refactor *(clean)*

The store reviewer compiled the pre-refactor `AutonomyCompanionStore` alongside the current one and ran
both against **copies** of `cs2_sample_layout`. For six operations — plain load→save, `renamePage`,
`deletePage`, `moveTiles` over 26 shifted squares, `forgetTiles`, and `snapshotPage` + destroy +
`restorePage` — the resulting `setup.json` and `configuration-Main.json` are **byte-identical** between
the two builds. The plain round trip is also byte-identical to its input.

Site-by-site reading confirmed ordering is preserved where it mattered (values before keys on the pair
maps, list values before keys on the list maps, `forgetSquares` still before the moves), that the
caption exception applies to captions only, that `ListMapKept` copies its lists in both directions, and
that the snapshot key change has no external reader.

This is the largest change of the day and the one with the most to lose. It was checked hardest and
came back clean.

### LD-D4 — message bundles, generated GUI blocks, and the `NO_OPTION` sweep *(clean)*

All 47 keys added or changed that day exist in all eight bundles, are pure ASCII, and carry identical
placeholder sets. Every `GEN-BEGIN`…`GEN-END` block in the thirteen changed GUI files is byte-identical
across the range. Every new dialog defaults to the safe answer on `CLOSED_OPTION`, and the six
`!= YES_OPTION` fixes from the previous round are still in place.

### LD-D5 — `clearedEdges` lifecycle and atomic/non-atomic equivalence *(clean)*

All four removal sites are paired with `activeLocomotives`, a fresh set is created per dispatch, and the
one path that leaves an entry behind does so deliberately for a Layout being discarded. The tail
bookkeeping populates identically in both `atomicRoutes` modes — the `continue` skips only the unlock —
so the claim that clearance is "the same computation that decides when an edge is safe to unlock"
holds.

### LD-D6 — a callback-verdict shape that is fragile but not vacuous *(examined, not ranked)*

`testAHandDispatchedTrainProtectsItsDestination` records its verdict with a bare `set()` in a callback
that the reviewer confirmed **fires twice** on a one-edge path — the same shape as a vacuous test found
the previous day. It is not vacuous today: both mutations produce `[false, false]`, so it fails
correctly. The reviewer judged it worth one word (`compareAndSet`) rather than a finding, and did not
rank it. Recorded here so the next reader does not have to re-derive that.

## What this says about how the round went

The round that produced these defects ran four review passes and two validation passes, and closed with
a document describing what they had caught. They caught real things. They did not catch any of these.

The pattern is not subtle. **Seven of the nine are guards written the previous day, and every one of
them was found by running something.** A3 needed a probe with nothing locked. A4 needed a dispatch with
a speed of zero. B3 needed the mutation its own javadoc named, run eight times. A5 needed a fixture with
a home in the file rather than in a method call. The passes that missed them were reading code and
reasoning about it — which is exactly what produced the defects in the first place, so it is not
surprising that it did not find them.

Three narrower lessons, each of which cost something here:

**A new guard has two failure directions and reviewing one is not reviewing it.** Every guard added that
day was checked for "does it refuse the dangerous case". None was checked for "what does it refuse that
it should not", which is where A3, A4 and B2 all live. Adam had to say this out loud — "be careful with
auto disallowed routes to avoid regression" — before it was looked at, and he was right both times he
