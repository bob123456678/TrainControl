### AUS-B1 - the track diagram's autonomy menu binds a run to the wrong square after the editor includes a page

| | |

| **Where** | `src/org/traincontrol/gui/TrainControlUI.java` 4689-4756: the panel behind the viewer's menu is built once per session (`autonomyTileMenus == null \|\| autonomyTileMenusFor != session`) and `buildTileMenu(tile, null)` at 4756 is called on it without a `refresh()`; `AutonomyEditorPanel.java` 8968, the only writer of `runLeaders` (`runLeaders = session.runLeaders()` inside `refresh()`), which runs in the constructor and after each of the panel's own actions (`item()`, 2462) and nowhere else; `leaderOf` 8740-8745 answers the tile itself for a key not in the map; `buildTileMenu` 1205 binds every item to `leaderOf(tile)`.  `AutonomySession.runs()` 7444-7470 walks `graph.getTiles()`, and `TileGraph`'s constructor (612-625) leaves an excluded page's tiles out of the graph - so a page that is excluded when the panel is built has no entry in its run map.  `autonomyEditorClosed` (6600-6640) rebuilds the running layout and captures; it does not touch `autonomyTileMenus`. | **Gesture** | With a page excluded from autonomy (the live snapshot has three: 2, 3, 4), right-click any square on the track diagram once, so the menu panel exists.  Open the autonomy editor on that page, untick **Exclude this page from autonomy**, Save and close.  Back on the diagram, go to that page and right-click a square in the MIDDLE of a run of plain track |

What the menu is then built on is `leaderOf(clicked)` = the clicked square, because the run map was made while the page had no tiles in the graph and nothing has remade it.  Two items on that menu act through the target:

- **Segment Length...** calls `applyLength(squareTheLengthWouldGoOn(tile))` (1889) - the run leader in the editor, the clicked follower here.  `applyLength` (6633-6720) with nothing selected prefills `lengthShownFor(follower)`, which sums `runTilesOf(follower)` = `{follower}` (8712-8726), so the dialog opens on 0 for a run the editor has just measured; OK writes `setRunLength(follower, n)` to the follower alone.  The reducer adds every tile (`GraphReducer.sumLength` 1320-1330), so **the run now measures the leader's number plus the follower's** - SET-B3's double count, on the surface the fix did not reach.  The viewer's panel saves as it goes (its `onChanged` is `session.save()`, 4701-4720), so the number is on disk before the next click.
- **Connections > a direction** calls `session.setRunDirection(follower, routeId, direction)` (8591).  `setRunDirection` (7566-7575) looks the key up in `runs()`, which is keyed by LEADER, finds nothing, and takes the *"not part of a run at all - a lone tile"* branch: one square of the run is made one-way and the rest are left as they were.  The comment on the radio (8586-8590) names that outcome - *"a way to end up with a run that contradicts itself"* - as the thing writing to the run exists to prevent.

The window is exactly one action wide: the item's `item()` wrapper refreshes after the action, so the second right-click on the same run is bound correctly.  What makes it worth a B rather than a C is that the one action is persisted and is the two writes the run rule was built to keep single.  `flowMarks`, the other cache `refresh()` fills, is also stale on this panel but has no reader there - it feeds `annotation()` (8437), which the viewer never asks (D6).

**Twins.**  The editor's own panel is not affected: `setPageExcluded` calls `refresh()` (SET-D4) and a page switch builds a new panel (`arriveAt` -> `setAutonomyMode(null)` nulls it at 1621).  Exclusion is the only setup-driven input to `isRunTile` (7476-7492: feedback, disqualified or transparent type, route count, stub) - every other input is geometry, and geometry changes go through the track editor and `resetAutonomySession`.  So the sequence needs the include gesture; there is no shorter road to it.

**Prove it.**  In `core.testMassAssignLengths`, on `openARunOfTwoPlainSquares()` (sensor 1,1 - 2,1 - 3,1 - station 4,1), the two seams the SET-B3 test uses:

```
session.setPageExcluded("main", true);
AutonomyEditorPanel viewer = new AutonomyEditorPanel(session, null, () -> { });   // what buildAutonomyTileMenu builds
viewer.setMenuOnly(true);
session.setPageExcluded("main", false);                                             // the editor's checkbox, on ITS panel
AutonomyEditorPanel fresh = new AutonomyEditorPanel(session, null, () -> { });     // the control: a map made now
TileKey follower = fresh.squareTheLengthWouldGoOn(key(2, 1)).equals(key(2, 1)) ? key(3, 1) : key(2, 1);
assertNotEquals(fresh.squareTheLengthWouldGoOn(follower), follower, "precondition: the run has no follower");
assertEquals(viewer.squareTheLengthWouldGoOn(follower), fresh.squareTheLengthWouldGoOn(follower),
    "the viewer's menu binds a run square to itself after the page came back");     // RED: follower vs leader
```

The fix is one line in either of two places: `autonomyTileMenus.refresh()` before `buildTileMenu` at 4756 (the panel's own `refresh()` is `public final`, and it is what `item()` already runs afterwards), or `autonomyTileMenus = null` in `autonomyEditorClosed` beside the rebuild, so the next right-click rebuilds it as `resetAutonomySession` does.  The first is cheaper to reason about - the map is then never older than the click - and costs one `session.check()` per menu, which `item()` already pays per action.  Manual: the gesture above on **2 - Bottom** with Show Lengths and the autonomy layer on; the arrow appears on one square, and Segment Length opens on 0.

### AUS-C1 - Segment Length on a run rebuilds the graph once per square

`setRunLength` (8684-8697) writes each square of the run through `session.setTileLength` (7247-7251), and every one of those calls `touched()` (7899-7903), which is `rebuild()` (342-362): a new `TileGraph`, a new `GraphReducer`, `reduce()`, and `deriveStationIndex()` - a full builder construction - on the event thread.  A run of n squares is n of those, followed by the `setupChanged()` at the end, which rebuilds the running layout as well.  The walk one method over got this right: `assignStretchLength` (3038-3065) writes through `store.setTileLength` and calls `touched()` once, and the javadoc on `clearEveryTileLength` (7264-7273) says exactly why - *"every one of those calls touched(), which rebuilds the reducer - a full builder construction on the event thread"*.  SET-C3's shape, one door over.  On Adam's railway a run is a handful of squares, so this is a pause, not a fault.  **Fix:** a session door `setRunLength(Map<TileKey,Integer>)` or `setTileLengths(...)` that writes through the store and touches once, which is what the two bulk doors already are.

### AUS-C2 - the track-length clear says Cancel cannot undo it, and Cancel can

`autolayout.ui.confirmClearAllTrackLengths` ends *"This cannot be undone, and Ctrl+Z will not bring them back."*, and the javadoc on `clearAllTileLengths` (9660-9674) says *"There is no undo here and no file to restore from until the setup is saved."*  Both were true before OB-223 and are not now: `tileLengths` is in the `kept()` registry (`AutonomyCompanionStore` 4901), `sharedFields()` writes every kept collection into the snapshot (1880), `takeTheUndoPoint` takes that snapshot when the editor opens (`LayoutEditor` 535-542), and `discardAutonomyWork` (615-624) restores it through `clearShared()` + `readShared()` (2346-2361) before the window closes.  So in the editor, Cancel brings every length back - which is what SET-D1 traced for maxima, and the same mechanism.  `clearAllHomes`' javadoc beside it (9744-9760) says the opposite and is right: *"Nothing is written to disk here - like every other decision in this window it waits for Save, so a mistaken press is undone by Cancel."*

This is WK7-C2 unswept: the locomotive clear was found saying the wrong thing about Cancel, got two sentences - `confirmClearLocomotives` (*"Cancel puts them back; Save keeps the change"*) for the editor and `confirmClearLocomotivesAtOnce` (*"It is saved at once"*) for the viewer's menu, chosen by `page == null` in `clearLocomotivesWarning` - and `regression.testTheBulkClearSaysWhatCancelDoes` pins them.  The lengths clear is reachable from both surfaces too (Bulk Tools is on the ignored-square menu and the viewer's menu, 1190-1200), and on the viewer's menu the sentence IS true, since that panel saves as it goes.  `confirmClearAllMaxTrainLengths` says nothing either way, which is at least not wrong.  **Fix:** the same two sentences the locomotive clear has, chosen the same way; and a `testCancelPutsTheLengthsBack` beside `testDiscardOnTheWayOutPutsTheHomeBack` in `regression.testCancelUndoesAutonomyEdits`, which today covers arrows, placements and homes and not lengths.  All eight bundles.

### AUS-C3 - the Unmeasured Track wash does not follow a run being closed

`annotationsChanged` (8838-8850) is the light door: it redraws the arrows through `onAnnotationsChanged` and posts the running-layout rebuild, and unlike `setupChanged` (8887) it does not null `unmeasuredSquares`.  That was safe as long as the legs did not depend on what the light door changes - and they do.  `GraphReducer.walkEdges` (991-1005) takes each step from `graph.exits(start, entry)`, and `TileGraph.exits` (774; 825 and 851) skips any route whose stored direction refuses the entry side, with `NONE` refusing both (`directionAllows` 1419).  So a run clicked through to **closed** - the cycle click (`cycle` 6992, `after()` 7290-7298 reaches `NONE` from `TOWARD_B`) or a radio set to *closed* on both ends of a run - takes its leg out of the reduction, `stretchesALengthRuleReads` no longer lists the piece, and `squaresNeedingALength` no longer contains its squares.  The menu's count follows at once (it is computed when the menu opens); the wash does not, because `annotation()` (8497-8499) reads the cache and the cache was filled before the click.  Opening a closed run back up is the mirror: its squares are unmeasured again and stay unwashed.

Of the four ordinary ways a direction is changed, one already refreshes first - the radio item (8596, `refresh()` before `annotationsChanged()`); **All branches** is a menu item and gets `item()`'s refresh; the cycle click (7050) and the One-Way tool (6841) reach `annotationsChanged()` alone.  The One-Way tool sets `TOWARD_A`/`TOWARD_B`, under which the leg survives in one direction and `legsOnce()` collapses the two directions to one tile set, so the tool cannot change the leg set on its own; the cycle click can.  MT-455's expected line is *"the number and the wash never disagree"*.  Cosmetic: the next menu action or Control+E puts it right, and a closed run is track autonomy will not use.  **Fix:** `unmeasuredSquares = null` at the top of `annotationsChanged`, which is the line `setupChanged` has and MAL-B3's own reason for it.

### AUS-C4 - the stretch prompt names an unnamed sensor by its raw key

`nameForPrompt` (9574-9598) names a switch by *"the switch at x,y"*, a crossing by *"the crossing at x,y"* since SVA-C3, and anything else by `getPointName(tile)` or, when there is none, `String.valueOf(tile)` - which is `TileKey.toString()` (`TileGraph` 133-136), *"page:x,y"*.  A piece ends at every sensor on the leg, station or not, so a sensor nobody has named yet puts `1 - Main:5,1` into *"Stretch 3 of 12, between 1 - Main:5,1 and Platform 2"* - the sentence SVA-C3 was about, for the square kind it did not list.  Reachable on any page with a sensor added since the last **Name Everything**; not checkable against the live snapshot, whose `pointNames` has 45 entries against 35 `s88` tiles on 1 - Main and its other pages excluded.  **Fix:** a `sensorAtSquare` key beside the other two, *"the sensor at {0}"*.

## Seen outside my scope

- `TrainControlUI.buildAutonomyTileMenu` (4689-4756) is where B1's fix would go, and it is `gui/**`.  Its comment at 4698-4703 explains why the panel's constructor-time `refresh()` must not save; a `refresh()` before `buildTileMenu` would run with `listening[0]` already true and so would save on every right-click - which `item()` already does after every action, but a reader adding the line should know it is a save as well as a redraw.  Resetting `autonomyTileMenus` in `autonomyEditorClosed` avoids that question.
- `GraphReducer.walkEdges` honours the stored directions through `TileGraph.exits` - which is right, and is the reason the editor's `unmeasuredSquares` cache has a fourth input (C3) that `SET-D4`'s list of three did not name.
