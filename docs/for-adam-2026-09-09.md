### 1. "Unavailable While Occupied" is enforced by Return Home, and the document says it should not be

**What the feature is.** You can mark a station as unavailable while some other square has a train
standing on it - a platform that cannot be used while the neck outside it is occupied, for instance.
The railway then refuses to send a train INTO the held-back station for as long as the watched square
is occupied. A train LEAVING the watched square is exempt, which is your own ruling: *"The condition
should not apply to trains leaving - only departing."* The restriction is about the whole block, so a
train on any copy of a split square counts as standing on it.

**Where it is enforced.** In the path check, behind a gate that asks whether full autonomy is running.
So autonomy enforces it, and a hand-driven send does not - you can always send a train wherever you
like, which is the tier split the document describes.

**The problem.** The Return Home planner applies the same restriction with **no such gate**. So the
real answer is: autonomy enforces it, manual does not, **and Return Home does**. The behaviour
document's opening section says *"Return Home sits with Manual on the question of where a train may be
sent"*, and lists exactly one exception to that. This would be a second one, and it is not written
down anywhere.

**Why I did not just write it.** Documenting it would state a second exception to your own ruling as
settled fact. The code is unambiguous about what it does; what it *should* do is yours.

**The choice.**

- **(a)** Return Home is right to enforce it. I write the exception into the document: Return Home
  sits with Manual except that it honours occupancy restrictions, and here is why.
- **(b)** Return Home should not enforce it - it is a hand-driven tier and you should be able to send
  a train home regardless. I remove the check from the planner and the document stays as it is.

This is the one that most blocks acceptance, because a document that is wrong about which tier
enforces a rule is worse than one that says nothing.

### 2. The orange arrows: which arrows, and is orange still the right colour?

**What you asked for.** *"We should draw arrows to manual-only destinations in a different color, like
orange."* A manual-only destination is a station you can send a train to by hand but that autonomy
will never choose for itself - the parking marking.

**Two problems, neither of which I can settle for you.**

**Orange already means two things on the running diagram.** It is the line showing where a train is -
which you chose this morning, replacing the grey wash - and it is the badge meaning "autonomy leaves
this square alone". That badge is already on exactly the squares you are asking to mark. So a
manual-only destination is already orange, in its badge, and adding a third orange thing risks the
colour meaning nothing.

**There is no drawing today whose subject is "arrows to destinations".** There are three families of
arrow and none of them is that:

- the **one-way restriction arrows** drawn on track, green and red, saying which way trains may run;
- the **station arrival chevrons**, yellow, hollow grey when an arrival side is barred - and these are
  drawn ONLY where a side is actually restricted, so on a plain parking berth there is no chevron to
  recolour;
- the **editor's traced-path arrows**, yellow out and orange back, which belong to the path-testing
  tool rather than to the railway.

**The choice.**

- **(i)** Recolour the arrival chevrons at a manual-only berth. Cheapest, but invisible on most
  parking tracks for the reason above - you would see no change where you most expect one.
- **(ii)** Recolour the one-way restriction arrows on the track leading into such a berth. That puts a
  third meaning on the red/green direction vocabulary, which currently says one thing only.
- **(iii)** A new overlay: select a train, and see an arrow drawn to each destination it may be sent
  to - the ones autonomy would choose in one colour, the manual-only ones in orange. This is new
  drawing rather than a recolour, and it is the most literal reading of what you asked for. If this
  one, I also need to know whether it is always on or behind a toggle, and whether it follows the
  train you have selected or the square you right-clicked.

### 3. The switch keyboard already asks about the power

**What I found.** It already does, and it did in the build you tested. The keyboard asks the power

same way. It was added on 2026-09-02, five days before the ticket was written, and it is present in

**Why the ticket exists anyway.** It was split out of an older ticket and carried that ticket's
original question forward, after the ruling had already been acted on. I also swept for a different
unguarded door in case you had clicked something else: every one of the 64 keyboard buttons goes
through the same guarded path, and the only other places that command an accessory are the diagram

**The choice.**

- **(a)** Mark it done - it is already what you asked for.
- **(b)** You want the two copies collapsed. The tile and the keyboard each have their own copy of the
  power dialog. They agree today in wording, options and Escape handling, but they are two copies of

  defects. Say the word and I make them one predicate.

### 4. "A compulsory turn is not somewhere autonomy sends trains" is true only by accident

**What the document says.** The reversals section has a table of what each kind of square is. One row
covers a **compulsory turn** - a square you have marked so that every arrival turns round there - and
says it should not be a destination autonomy chooses for itself.

**What the code does.** The flag that means "autonomy will not choose this" is only ever written for
the parking marking - the one you set by hand to mean manual-only. It is never written for a
compulsory turn. And a must-turn station is built as a terminus, so the runtime's other test for a
turning square does not catch it either. The result is that autonomy will happily choose a compulsory
turn as a destination **unless you have also marked that square as parking**.

**So the row is true of your railway today** - because of how you happen to have marked those
particular berths - rather than being a property of the system. There is also a related helper in the
editor that adds compulsory turns to the list of stations autonomy will not choose, whose comment
claims to mirror the runtime rule; it does not.

**The choice.**

- **(a)** The table is right and the code should enforce it: the builder sets "autonomy will not
  choose this" for every compulsory turn, and the row becomes true by construction.
- **(b)** The code is right and the table overstates it: marking a square as a compulsory turn says
  what happens when a train arrives, not who may send one, and keeping the two separate is deliberate.
  I reword the row to say so.
